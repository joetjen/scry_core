# Changelog

## [Unreleased]

### Added

- Set comparison operators `⊂`/`⊆`/`⊃`/`⊇` (lang_spec.md §5.9, ISO 80000-2), each with a word-form alternative spelling (`subset of`, `subset or equal to`, `superset of`, `superset or equal to`) -- a real gap found by a spec-traceability audit, entirely absent before this. `⊂`/`⊃` are *proper* subset/superset (the same relationship `<` has to `<=`, one level up -- a set tied with itself is neither), `⊆`/`⊇` allow the tie. Both spellings of a given operator resolve to the identical `{:cmp, :subset | :subset_eq | :superset | :superset_eq, lhs, rhs}` predicate shape -- `Scry.Core.Actions`' own word-form handlers ignore their captured keyword token and return the matching symbol's own text directly, so nothing downstream (`op_from_text/1`, `Scry.Core.QueryOps.compare/3`, every caller) needs a separate word-form branch. Comparison is structural (`MapSet`-based, lang_spec §3's own "compound values compare by content" rule extended one level up) -- duplicate/reordered elements on either side never affect the result. A non-list operand is a real, clear `ArgumentError`, not a silent wrong answer, the same "hard error over silently wrong" posture null-safety (§7) already takes. New keywords `subset`/`superset`/`of`/`equal`/`to` (case-insensitive, via `Scry.Core.Grammar.KeywordRefiner`, same as every other structural keyword). Negation works via the ordinary `not (...)` idiom lang_spec §5.9 itself states -- no new grammar needed. `test/scry/core/actions_test.exs`, `test/scry/core/executor_test.exs`.

- Bitwise `&`/`|`/unary `!` and unary `-` (lang_spec.md §5.10, and the precedence-table's own tiers 1 and 5) -- a real gap found by a spec-traceability audit, not previously implemented at all. `expression` (the arithmetic/bitwise chain's own former top-of-precedence name) now names the widest tier (`& |`, binding looser than `+ -`), with the former rule renamed `additive` one tier down -- every existing external call site (`order_item`, `call_arg`, `when_expr`/`when_clause`, `field_body_item`, `primary`'s own parenthesized grouping) already referenced `expression` by name, so all of them gain bitwise operators for free with zero signature changes. `unary` (tier 1, tighter than `**`) sits directly below `power`'s own base, recursing into itself so a doubled prefix (`--x`, `!!flag`) parses too. New AST tags `{:bitwise, :band | :bor, expr(), expr()}` and `{:unary, :neg | :bnot, expr()}` on `Scry.Core.Query.expr()`, threaded through every existing `{:arith, ...}` walker (`expr_has_call?/1`, `expr_has_aggregate_call?/1`, `resolve_rhs/4`, `resolve_group_rhs/5`, `rewrite_expr/2`). Bitwise operands are integer-only -- `Scry.Core.Rational`'s own numeric tower has no bitwise closure, so a non-integer operand (a genuine fraction, or a float) is a real, honest `ArgumentError`, not a silent wrong answer, the same "hard error over silently wrong" posture null-safety (§7) already takes. Unary minus stays in the exact-rational tower (`Rational.sub(0, a)`), so `-3/2` is still exact, not a special case. `test/scry/core/actions_test.exs`, `test/scry/core/executor_test.exs`.

- New public `Scry.Core.QueryOps.resolve_correlated_nested/5` -- resolves one nested-`SELECT` body item against one outer row, correlating any `{:field, [own_name, field]}` reference in its own `wheres` (the identical correlation `run_document/4`'s own internal `expand_row/7` already performs for an ordinary `EngineBehaviour`-based engine), as a standalone, reusable primitive. Found necessary building `scry_reldoc`: `run_flat/3` is explicitly "flat" (this module's own moduledoc already stated it operates only over rows already in hand) and genuinely cannot resolve a nested `%Scry.Core.Query{}` body item at all -- confirmed the hard way, not assumed (`project_item/3` has no clause for a bare `%Query{}`, a real `FunctionClauseError`, not a documented decline). A kind package whose own executor bypasses `EngineBehaviour` entirely (`scry_document`/`scry_graph`, needing the whole document/graph space rather than one already-resolved source) has no way to reach `run_document/4`'s own whole-query orchestration either, since that function fetches every flat leaf via `engine_module.execute/3` -- a contract neither package's own bespoke `conn` implements. This factors out just the correlation-rewrite step (`rewrite_correlation/3`, already private in this module) so such a package can resolve a nested `SELECT` sibling of its own kind-specific pseudo-fields correctly, via a caller-supplied `fetch_fn` (typically recursing back into the caller's own top-level `run/3`), without duplicating `AND`/`OR`/`NOT`/`IN`-aware correlation semantics independently. See `scry_document`'s/`scry_graph`'s own `CHANGELOG.md` for how each package now uses it. `test/scry/core/executor_test.exs`.

- New `%Scry.Core.Query{}.goal_args` field (`[expr()] | nil`, default `nil`) -- a call-shaped source, `SELECT <name>(<args>) { ... }` (lang_spec.md §8.4's `logic` variant: `SELECT ancestor(X, "bob") WHERE age(X) > 30 { X }`). Plain core grammar (a new `goal_args := LPAREN call_args? RPAREN` production, reusing `call`'s own `call_args` verbatim), not gated to `logic` at the grammar level -- `source` itself parses exactly as any other bare source name always has (`["ancestor"]`), with the parenthesized argument list threaded through this new, additively-defaulted field instead, the same "genuine top-level field, not `variant`, zero behavior change for a query that never sets it" shape `time_field` already established. An argument is any ordinary `expr()`, including a bare field reference (`{:field, ["X"]}`) -- no new "this is a logic variable" syntax; a kind's own executor decides that at execution time (a bare, unqualified single-segment `{:field, [name]}` argument is a variable keyed by `name`).
  `Scry.Core.TypeCheck`'s own category check (§1) gains a matching clause: a non-nil `goal_args` against a `TYPE` declaring a real, non-`nil` `kind` other than `"logic"` is a hard `{:kind_category_mismatch, source_name, kind, [:goal_args]}` error, the same "grammar answers whether a construct exists, the category check answers whether it's legal here" split `via`/`last`/`deep` already have. An unregistered source, or one with no declared `kind` at all, stays silent, matching every other check's existing leniency.
  Found and fixed along the way: `priv/grammar.aether`'s own pre-existing comment on `select_ep1a`/`where_clause` (an *explicitly renamed* optional rule reference, `name:rule?`, resolves via raw source-text concatenation, not real evaluation -- only a *bare* `rule?` dispatches to `handle_rule` and is genuinely absent when unmatched) applied to this new grammar too; the first draft used `goal_args:goal_call_args?` and `args:call_args?`, both silently wrong in the same way, caught empirically (not from re-reading the existing comment closely enough the first time) before landing the bare-reference shape that actually works.
  `test/scry/core/actions_test.exs`, `test/scry/core/type_check_test.exs`, `test/scry/core/grammar_parity_test.exs`.

### Fixed

- `priv/grammar.aether`'s own `body_list` (a `SELECT`'s `{ ... }` body) now implements lang_spec.md §6's item-separation rule for real: a comma is required only when two items share a physical line, a bare line break suffices when each item is on its own line, and a trailing comma before the closing `}` is permitted -- previously `COMMA` was required unconditionally, on every line break or not, a real, long-documented gap (this file's own `body_list` comment used to flag it directly). `SELECT users {\n  name\n  email\n}` (no commas at all) now parses.
  Two dead ends tried and abandoned first, kept as comments in `priv/grammar.aether` itself: (1) a dedicated `NEWLINE` token pulled out of skip-trivia -- `Grammar.VM.Tokenizer`'s own maximal-munch tokenizer is a single, whole-file, context-free pass over every declared token, so any new token whose character class overlaps `SPACE`/`COMMA` inevitably competes with them at every position those already appear, corrupting ordinary comma-separated constructs (call args, `GROUP BY a, b`) everywhere else in the grammar, not just here; (2) detecting the separator via ordinary suppressed (`~`) rule composition and right-recursion (`body_list_tail`) alone -- necessary, but not sufficient: `body_item`'s own trailing optional lookaheads (`field_body_item`'s `if_clause?`, `path`'s own dotted-segment repetition) unconditionally splice past any trivia while checking for a construct that usually isn't there, silently consuming the very newline `body_list_sep` needed to see, whether or not the lookahead itself matched. New `Scry.Core.Grammar.BodyListSep`, a rule-position `@native` callback (distinct from the token-position `@native` `BlockCommentLexeme` already uses), sidesteps this by reading the compiled token stream directly -- scanning forward from the current position for the ordinary case, and backward for the leaked case (the trivia is still a real, distinct token in the stream; only the parser's position moved past it) -- robust regardless of how much upstream composition happened to consume. `body_list_sep` always matches structurally (never a hard grammar rejection, so the failure surfaces as a real, specific error message rather than a generic "input does not match"); `Scry.Core.Actions.handle_rule(:body_list_sep, ...)` is what turns a same-line, no-comma classification into `{:error, ...}`.
  `test/scry/core/actions_test.exs` (a new "body-item separator" describe block, including a property test over arbitrary comma/newline mixes and a regression case for the `if_clause?` leak specifically), `test/scry/core/grammar_parity_test.exs` (VM vs. compiled-native agreement on the same cases), `test/scry/core/grammar_compose_test.exs` (updated for `body_list`'s new right-recursive capture shape).

### Added

- New third extension point, `comparison_ep1e` (`priv/grammar.aether`'s own `comparison` production, `Scry.Core.GrammarCompose.extension_points/0`) -- EP1(e), an infix comparison-tier operator (lang_spec.md §2/§8.5's `SEARCH`), joining `select_ep1a`/`body_item_ep1`. Built the same union-of-simultaneous-contributions way as the other two (`NEVER` default, `merge_maps`/`union_rule` unions each loaded fragment's own contribution), not a special case. A kind's own fragment produces a `predicate()` core can't interpret on its own, tagged `{:variant, term()}` -- `predicate()`'s own new leaf shape, `body_item()`'s own `{:variant, term()}` idiom's counterpart one level down. Unlike a `:variant` body item (only ever a whole body item), this leaf can appear nested arbitrarily deep inside `{:and, ...}`/`{:or, ...}`/`{:not, ...}`, in either `wheres` or `havings` -- `Scry.Core.EngineBehaviour`'s own "what a kind package must guarantee" contract is extended to require a full tree walk, not just a top-level check, before calling `Scry.Core.Executor.run/3,4`. A `{:variant, ...}` predicate reaching generic evaluation unresolved now raises a clear, named `ArgumentError` (`eval_predicate/4`, `eval_group_predicate/5`) instead of an opaque `FunctionClauseError` -- found and fixed the identical gap in two more predicate-tree walkers along the way (`streaming_predicate_calls/1`, `predicate_has_aggregate_call?/1`), both of which previously had no catch-all for this new shape either. `test/scry/core/grammar_compose_test.exs`, `test/scry/core/executor_test.exs`.

- **Breaking**: `order_bys` (`%Scry.Core.Query{}`, and the `{:window, ...}` expr tuple) widens from a bare field path (`[String.t()]`) to a full `expr()` -- lang_spec.md §8.5's own `ORDER BY relevance() DESC` needs a call there, not just a field, and `ORDER BY price * quantity DESC` falls out for free for every kind, not a search-specific carve-out. `priv/grammar.aether`'s `order_item` (`field:path` → `key:expression`) now produces the same `{:field, path}` tag any other `expr()` position already does for a bare field reference -- the common case is unaffected in *behavior*, only in the literal shape of the parsed AST (`{["age"], :desc}` is now `{{:field, ["age"]}, :desc}`). Fully backward compatible at the *resolution* layer, not just the parser: a new `resolve_order_key/4` helper (used by `sort_rows`/`sorts_before?`/`ties?`/`rank_at` and friends) still treats a bare `[String.t(), ...]` list exactly as before (a direct `get_path` lookup), so every hand-built `%Scry.Core.Query{}` anywhere in this ecosystem that already writes bare-list `order_bys` keeps working unchanged -- only newly-parsed text queries and the Elixir-native builder's own output shape change. `Scry.Core.Query.Escape.escape_order_by_entries/3` now escapes via `escape_expr/3` (not `escape_path/3`), so `order_by: [desc: relevance()]`/`order_by: [desc: u.price * u.quantity]` both work from the composable builder too. `sort_rows/3→4`, `sorts_before?/4→5`, `insert_topk/5→6`, `insert_sorted/4→5`, `rank_at/4→5`, `count_ties_before/4→5`, `ties?/4→5` all gained a trailing `params` parameter to support resolving a call (`resolve_rhs/4` needs it) -- mechanical, no behavior change for a bare-path key. `test/scry/core/executor_test.exs`, `test/scry/core/query/escape_test.exs`, `test/scry/core/actions_test.exs`.
  **Downstream consequence, fixed in the same effort**: `scry_engine_exqlite`/`scry_engine_postgrex`'s own SQL compilers pattern-matched the old bare-path shape directly to translate `ORDER BY` to native SQL -- both updated to unwrap the common `{:field, [single]}` case back to a plain column reference (same pushdown coverage as before; anything more complex still correctly declines via `{:unsupported, {:order_by, ...}}}`). See both packages' own `CHANGELOG.md`.

- New `rate(<duration>)` built-in aggregate (lang_spec.md §5.8/§8.2), alongside `sum`/`avg`/`count`/etc in `@aggregate_names` -- an events-per-time-unit computation (LogQL's own `rate()` flavor, not PromQL's counter-reset-compensated slope): `count(rows in scope) * duration / elapsed`, `elapsed` measured via the group's own min/max value of whichever field a new `%Scry.Core.Query{}.time_field` names. `time_field` is a genuine top-level struct field (default `nil`, zero behavior change for every kind that never sets it) rather than living in `variant` -- `variant` must be emptied before `Scry.Core.Executor.run/3,4` runs (`EngineBehaviour`'s own contract), but `time_field` is allowed to survive past that point, since it's read only much later, by `rate`'s own aggregate computation. `rate`'s own duration argument is deliberately independent of whatever populated `time_field` (e.g. `scry_time_series`'s `LAST <duration> OF <field>`) -- two unrelated numbers, not a default/override pair. Works as an ordinary aggregate (flat or `GROUP BY`-scoped), in `HAVING`, and reused as a window function (`rate(...) OVER (...)`) -- the same three contexts every other aggregate already supports, via the same `@aggregate_names` membership. Deliberately excluded from `@streaming_capable_aggregate_names` (needs the group's full row set to find min/max timestamp, not a simple running fold -- same reason `percentile`/`stddev*`/`var*` are excluded). `eval_aggregate/5` and its full call chain (`resolve_group_lhs/rhs`, `eval_group_predicate`, `having_matches?`, `project_group`/`project_group_item`, `augment_with_window_values`, `compute_window_values`, `window_value`) all gained a trailing `time_field` parameter to thread it through -- a mechanical arity widening, not a behavior change for any existing aggregate. `Scry.Core.Query.Escape`'s `@call_names` (the Elixir-native builder's own recognized-function list) gains `"rate"` too, so `from u in "metrics", select: %{r: rate(5)}` escapes correctly. `test/scry/core/executor_test.exs`, `test/scry/core/query/escape_test.exs`.

- New `Scry.Core.QueryTool`, and generic `mix scry.query`/`mix scry.iex` Mix tasks built on it -- moved here from `scry_test_core`, where both tasks originated hardcoded to that package's own four `Scry.Test.Core.Conn` constructors. Any project depending on `scry_core`, directly or indirectly, now gets both tasks for free (Mix's own task discovery scans every dependency's compiled tasks regardless of `only:`/`runtime:` scoping -- no extra registration needed), config-driven rather than hardcoded since `scry_core` can never depend on a `scry_<kind>` grammar or `scry_engine_<driver>` connection package (they depend on it): `config :scry_core, :query_tool, parser: Module, default: "name", backends: %{"name" => {Module, :zero_arity_fun}}`. `--backend NAME`/`--parser MODULE` override the configured default/parser per invocation. Deliberately config-driven, not dependency-tree auto-detection -- the latter shape (dynamically composing/dispatching based on what's installed) was already tried once for grammar composition specifically and explicitly abandoned (impl_spec.md §4/§8: "which kind libraries are loaded is a build-time, not runtime, property"), so repeating it here for backend/parser discovery would be a new departure from an already-settled, empirically-justified project policy, not a neutral choice.
  `Scry.Core.QueryTool.run/3`/`execute/2`/`resolve_parser/1`/`resolve_backend/1`/`format_error/1` are the same resolution/parse/execute/materialize/format logic both original `scry_test_core` tasks used, byte-for-byte, now de-duplicated into one tested module instead of two independent copies. `test/scry/core/query_tool_test.exs`.

- `execute/2` gains a configurable `executor:` key (`config :scry_core, :query_tool, executor: {Module, function}`, defaulting to `{Scry.Core.Executor, :run}`, called as `function(query, engine, conn)`) -- found needed migrating `scry_test_time_series`, not designed speculatively ahead of that: `Scry.TimeSeries.Executor.run/5` (not `Scry.Core.Executor.run/3`) is what actually understands `LAST <duration> OF <field>`/`LAST <from> TO <to> OF <field>` (`Scry.TimeSeries`'s own moduledoc has the full "why a separate executor, not a special case in core" reasoning), so a kind package whose grammar needs its own execution semantics wires this key alongside `parser:`. `Scry.TimeSeries.Executor.run/5`'s own two further, defaulted arguments (`params`, `now`) resolve to a real, callable `run/3` via Elixir's own default-argument arity generation -- no shim needed on either side for the common case. `test/scry/core/query_tool_test.exs` gains a case asserting the configured executor is actually called, not just `Scry.Core.Executor` by coincidence.

- The inline half of lang_spec.md §7's compile-time type system: new `Scry.Core.TypeCheck` reads `type_decls` off a parsed document and, for every query node whose own single-segment `source` byte-for-byte matches a declared `TYPE`'s name, runs (1) a category check (a degenerate `relational`/`olap` kind with a non-empty `variant` is a hard error), (2) a declared-field-type/union comparison check against a literal (currently `Int`/`String`, the only two scalar names lang_spec.md actually specifies), (3) `JSON<Type>`/`DXN<Type>`/`DXNB<Type>` field-access validation against a declared shape (a bare structured field, or one with no declared shape, accepts any dot-path with no validation, same leniency as before), and (4) flow-sensitive compile-time null-safety narrowing that mirrors `Scry.Core.QueryOps.eval_predicate/4`'s own runtime `AND`/`OR` short-circuit order exactly (`age > 30 AND NOT (age = nil)` still fails at compile time; guarding first passes). Wired unconditionally into `Scry.Core.Actions.handle_rule(:document, ...)`, right after `type_decls` itself is attached -- a document with no `TYPE` declarations at all sees zero behavior change. New `Scry.Core.TypeCheck.Nodes`, the shared tree-walk primitive (`each/2`/`collect/3`) both this module and `Introspection` below use, reusing the same recursion targets `Scry.Core.WithCycleCheck` already established (nested `select` queries, every `with_bindings` value, both sides of a `CombinedQuery`).
  `DXN`/`DXNB` (dextrin's text and binary/CBOR encodings of "the same value space") join `JSON` as first-class structured field types, symmetric in every respect the compile-time checker cares about -- it never distinguishes the three beyond recognizing which name matched; decoding any of them at execution time remains a separate, out-of-scope adapter concern, same as `JSON` already had. The canonical spelling for all three is now all-caps as a *type name* (`JSON`/`DXN`/`DXNB`, not `Json`/`Dxn`) -- a real correction to existing usage, not just new-feature styling; the lowercase cast/function forms (`json(field)`, `dxn(field)`, `dxnb(field)`) are unaffected, mirroring the pre-existing `Int` type name vs. `string(...)` cast function asymmetry.
  The introspection-assisted half: `Scry.Core.EngineBehaviour` gains an optional `describe_source/2` callback (`{:ok, [introspected_field()]} | {:error, :not_found} | {:error, {:introspection_error, term()}}`) and new `Scry.Core.TypeCheck.Introspection.check_with_introspection/3`, invoked via a new `Scry.Core.check_types/3` facade -- explicitly opt-in, called by an application between `parse/1` and `Executor.run/3,4`, never automatically (it needs a live connection; `parse/1` stays a pure string-in/struct-out function). Fills in a `type_decl` for any real source referenced with no inline `TYPE` at all (excluding `WITH` binding names); a source with even one hand-declared field is filtered out of the introspection candidate set entirely -- inline wins completely if present at all, no field-by-field merge.

### Fixed

- `Scry.Core.QueryOps.rewrite_predicate_correlation/4` (the nested-`SELECT` correlation rewriter, run before a nested leaf's own `wheres` ever reaches `eval_predicate/4`) also lacked a `{:variant, ...}` clause -- found building `scry_search`: a nested `SELECT` combining real ancestor correlation with an (incompletely lowered) `SEARCH`-shaped predicate in the same `wheres` crashed one step earlier than `eval_predicate/4`'s own already-fixed rejection, inside correlation rewriting itself. Fixed the same way -- pass an unresolved `{:variant, ...}` predicate through unchanged, the same "opaque, no-op" treatment its sibling `correlation_refs/2` already gives it via its own pre-existing generic catch-all. `test/scry/core/executor_test.exs`.

- `Scry.Core.TypeCheck`'s three predicate-tree walkers (`walk_type_check/3`, `walk_json_check/2`, `check_predicate/4`) all lacked a `{:variant, ...}` clause -- found building `scry_search`: parsing *any* query using the new `SEARCH` operator (comparison_ep1e) crashed with a raw `FunctionClauseError` here, unconditionally, not gated behind a `TYPE` declaration existing at all (this compile-time pass runs on every parsed document regardless). Fixed by treating an unresolved `{:variant, ...}` predicate as inert at every one of the three checks (declared-field-type, JSON-path, null-safety narrowing) -- correct, since it's opaque to core until the contributing kind's own executor lowers it, the same "no-op" treatment the generic `{:cmp, _, _, _}` catch-all already gets at each site. `test/scry/core/type_check_test.exs`.

- `Scry.Core.Row` is now genuinely usable everywhere `Scry.Core.QueryOps` processes a row, not just `WHERE`/`GROUP BY`/sorting/projection as previously documented (and previously true only by coincidence, not by design) -- found wiring a real engine (`scry_engine_exqlite`) to return `Row` values directly from `execute/3`: nested-`SELECT` correlation (`rewrite_side_correlation/4`) read an outer row's field via a raw `Map.get/2`, which silently returns `nil` for a `Row` struct (a `Row` has no such literal map key -- `Map.get/2` doesn't know to look inside its `index`/`values` fields) instead of raising or resolving correctly; nested-`SELECT` expansion (`expand_row/7`) and window-function synthetic-column augmentation (`augment_with_window_values/4`) both appended a new key via a raw `Map.put/3`, which "succeeds" on a `Row` struct (Elixir structs are maps at the BEAM level) while silently producing a corrupted, unusable `Row` with a stray extra key `Row.fetch!/2`/`Row.to_map/1` never see. Fixed via a new private `put_field/3` helper (converts to a plain map on first synthetic-field write, the same way appending a genuinely new column already isn't representable by this fixed-shape type) and switching `rewrite_side_correlation/4` to the existing, already-`Row`-safe `get_path_in/2`.
  `Scry.Core.QueryOps`'s own `CombinedQuery` handling (`UNION`/`INTERSECT`/`EXCEPT`) now also normalizes both sides to plain maps before combining -- those operations do real structural-equality set comparisons (`Enum.uniq/1`, `MapSet.member?/2`), and a `Row`'s own equality is tied to its *positional* shape (its own `index`), not just its logical field values, so two engines that happened to build their own index in a different column order could otherwise wrongly compare unequal (or, worse, wrongly compare equal by position coincidence). A nested-`SELECT`'s own result list is likewise always normalized to plain maps now, regardless of what shape the nested query's own engine returned internally -- consistent with the "final projected shape is always a map" rule `project/3` already established, and free of charge relative to the per-outer-row correlation cost already being paid.
  New `Scry.Core.Test.RowReferenceEngine` (test support) proves all three fixes end to end: a correlated nested `SELECT`, a window function computed over a `WITH`-bound source, and a `UNION` -- each run against a `Row`-returning engine and asserted to produce results identical to the plain-map reference engine.

### Removed

- **Breaking**: `Scry.Core.EngineBehaviour`'s `fetch/2`, `fetch/3`, `fetch/4`, and `aggregate/5` callbacks are gone entirely, along with everything in `Scry.Core.Executor` built around them: the `fetch/4`/`fetch_opts()` column-hint mechanism (`referenced_top_level_fields/2` and the whole `collect_predicate/expr/path/body_item` walker family), the `fetch/3`-then-`fetch/2` lenient-pushdown preference cascade, and the separate `aggregate/5` pushdown-plan machinery (`aggregate_pushdown_plan/3`, `pushdown_select_plan/2`, `groups_from_pushdown/2`, `try_aggregate_pushdown/6`). None of it is replaced by an equivalent; see Added below for what replaces the whole trust model.

### Added

- `Scry.Core.EngineBehaviour` gains a single required callback, `execute/3` (`conn, query :: Scry.Core.Query.t() | Scry.Core.CombinedQuery.t(), params -> {:ok, Enumerable.t()} | {:error, error()}`), plus an optional, purely descriptive `capabilities/1`. **A genuinely different, stricter trust model than the contract it replaces**: an engine now receives the *entire* query -- `WITH` bindings, nested/correlated `SELECT`, `UNION`/`INTERSECT`/`EXCEPT` combinators included, exactly as `Scry.Core.parse/1` produced it, not a guaranteed-flat fragment -- and is authoritative for whatever it accepts. Nothing downstream re-applies, re-verifies, or falls back to a different implementation of anything an engine returns; an engine that can't (or won't) compute a given query's shape must decline it via `{:error, {:unsupported, detail}}` rather than return something narrower.
  Motivated by measurement: even with the prior `aggregate/5` pushdown mechanism in play, a `GROUP BY`-heavy query against a real SQLite-backed table was still 11.5x-15.3x slower than the equivalent raw SQL (110.7s vs 7.25s at 1,000,000 rows), because `fetch/3`/`fetch/4`'s own lenient contract meant `Scry.Core.Executor` always re-applied its entire pipeline regardless of what got translated, and `aggregate/5`'s own authoritative contract never covered `avg`, `HAVING`, or `ORDER BY`/`LIMIT` pushdown at all. Closing that gap needed an engine trusted to own the entire query and its own result, which is incompatible with the automatic re-verification that made incremental `fetch/3`/`fetch/4` adoption safe in the first place.
  `Scry.Core.Executor.run/3,4`'s own public signature and `{:ok, Cursor.t()} | {:error, term()}` contract are unchanged -- it now does almost nothing itself, just calling `engine_module.execute/3` and wrapping a successful result in a `Scry.Core.Cursor.t()`. A correlated nested `SELECT` maps naturally onto a native SQL `JOIN` and a `WITH` binding onto a native CTE -- an engine sophisticated enough to translate the whole document into one native query is free to (`Scry.Core.Executor` never pre-decomposes it), and an engine that isn't (yet) can delegate some or all of it back to the new `Scry.Core.QueryOps` toolkit from inside its own `execute/3`, entirely its own choice.

- New `Scry.Core.QueryOps` module: the row-processing toolkit `Scry.Core.Executor` used to run automatically, extracted essentially verbatim (`WHERE`/`GROUP BY`/`HAVING`/every lang_spec.md §5.8 aggregate/`ORDER BY`/`DISTINCT`/`LIMIT`/`OFFSET`/projection/casts/window functions -- the exact per-row and per-group semantics, unchanged) behind two public entry points an engine calls entirely at its own discretion, never automatically: `run_flat/3` (given rows already in hand plus a flat query, computes the rest) and `run_document/4` (given a `conn`/engine module, additionally resolves `WITH` bindings, correlated nested `SELECT`, and combinators generically, recursing back into that same engine's own `execute/3` for each flat leaf).
  `run_document/4`'s own nested-`SELECT` handling is **scoped narrower than the interpreter it replaces, in two documented ways**, deliberately, rather than half-reproducing the old interpreter's full ancestor scope-chain: a nested query's own correlated reference must name its *immediate* enclosing query, not a grandparent or higher; and correlation is only detected in a nested query's own `wheres`, specifically a comparison's right-hand side (`{:field, [ancestor, field]}`), not `select`/`order_bys`. Both surface as a real, honest failure (an ordinary null-safety hard error, since an unresolved reference falls through as an unmatched literal path) rather than a silently wrong answer.
  A genuine, unplanned capability gain from this split: a nested `SELECT` inside a `GROUP BY` query's own `select` now works (previously a deliberate `{:error, {:unsupported_grouped_body_item, ...}}`), since `run_document/4` extracts nested items from `select` before ever handing the "shell" query to `run_flat/3` or a real engine -- grouped or not is irrelevant to that extraction.

- Fixed a real, previously-latent bug in `Scry.Core.Cursor.next/1`, found while building `Scry.Core.QueryOps.run_flat/3`'s own lazy `LIMIT` handling: a composed `Stream` stage that needs to stop its source early (`Stream.take/2`, on its own last allowed element) signals that via `{:halted, acc}` rather than `{:suspended, acc, continuation}`, and `next/1` previously treated every `{:halted, _}` as "no data," silently dropping that final, genuinely-produced element (`Cursor.new(Stream.take([1,2,3,4], 2)) |> Cursor.to_list()` returned `[1]`, not `[1, 2]`). Fixed by resuming with a fresh, VM-unique `make_ref()` sentinel instead of a bare `nil` -- disambiguates "this halt carries a real final element" from "this halt (`Stream.take_while/2`'s own rejecting predicate, e.g.) produced nothing new," which a bare `nil` couldn't, since a genuine row element can itself legitimately be `nil`.

### Changed

- `Scry.Core.Executor`'s streaming `GROUP BY`/aggregation path's internal per-group accumulator changes shape from `%{representative: row, aggs: %{{name, args} => acc}}` to a flat `{representative, aggs_tuple}` tuple, `aggs_tuple` holding one element per aggregate in the query's own (already-deduplicated) `plan` list, in `plan`'s own order. Measured motivation: real, in-situ profiling of a `GROUP BY user_id`-style query (1,000,000 rows, ~1,000,000 distinct groups) found the old nested-map shape cost ~1.8-2x more to build than an equivalent flat tuple, and that cost compounded further when the same structure was copied back across a worker `Task`'s process boundary -- together accounting for a large share of the streaming path's total time. A read by `{name, args}` (the only two places that need one -- `HAVING` evaluation and final projection) resolves its own tuple position via a direct `Enum.find_index/2` over `plan` at the point of use rather than a second precomputed index map, since `plan` is always tiny (1-5 entries) in practice. Purely an internal representation change -- `Scry.Core.EngineBehaviour.aggregate/5`'s own public contract, the `ROLLUP`/`CUBE` eager aggregation path, and window functions are all unaffected. Real before/after timing on the same 1,000,000-row/~1,000,000-group scenario: `GROUP BY user_id` through `Scry.Engine.Exqlite` went from 7.66s to 4.98s (a genuine 1.54x speedup), narrowing Scry's own overhead over equivalent raw SQL from 11.5x to 7.75x.
  `test/scry/core/executor/parallel_aggregation_test.exs` gains a case exercising an aggregate reachable only through `HAVING` (absent from `select` entirely) -- the one pre-existing `HAVING` test happened to use the same aggregate in both places, which couldn't have caught a position mix-up between the accumulator's build side and its read side for a `plan` entry reachable only one way. Every other existing test in this file and in `test/scry/core/executor/aggregate_pushdown_test.exs` passes unmodified.

- **Breaking**: every module's own namespace changes from flat `ScryCore.*` concatenation to a nested `Scry.Core.*` root -- `ScryCore.Query` is now `Scry.Core.Query`, `ScryCore.Executor` is now `Scry.Core.Executor`, and so on for every module this package exposes (`Scry.Core.Cursor`, `Scry.Core.EngineBehaviour`, `Scry.Core.CombinedQuery`, `Scry.Core.Rational`, `Scry.Core.Actions`, `Scry.Core.Grammar`/`.Compiled`/`.KeywordRefiner`/`.SigilLexeme`/`.BlockCommentLexeme`, `Scry.Core.GrammarCompose`, `Scry.Core.Query.From`/`.Escape`, `Scry.Core.Executor.QueryError`, `Scry.Core.FragmentResolver`, `Scry.Core.WithCycleCheck`). A pure, mechanical rename -- zero behavior change -- done first, deliberately, so every subsequent increment (engine-side query pushdown, real kind-independent adapter packages) is written directly against the final names instead of needing a second pass later. `lib/`/`test/` directory layout now mirrors the new module nesting (`lib/scry_core/query.ex` → `lib/scry/core/query.ex`, matching ordinary Elixir convention for a multi-segment top-level module) -- the `:scry_core` OTP app name/atom in `mix.exs` is unaffected, only the Elixir module namespace changes. `priv/grammar.aether`'s own `@native`/`@refine` hooks (`BLOCK_COMMENT`/`SIGIL`/`IDENT`'s keyword refiner) updated to the new module names, and `lib/scry/core/grammar/compiled.ex` regenerated fresh via `priv/gen/generate_compiled_grammar.exs` rather than hand-edited, per this project's own "never hand-edit a generated file" rule.

### Added

- `Scry.Core.EngineBehaviour` gains an **optional** `aggregate/5` callback -- real, native `GROUP BY`/aggregate pushdown, a genuinely stricter, authoritative-not-lenient contract than `fetch/3`/`fetch/4`'s own (its own moduledoc has the full reasoning: grouping is irreversible, so a wrong or incomplete pushdown can't be corrected downstream the way over-fetched rows can). Motivated by measurement: after the column-pruning/compact-row and `Rational` fast-path work below, a high-cardinality `GROUP BY` was still found to be ~8x slower than an equivalent native `Enum.reduce/3` over the same rows -- `Scry.Core.Executor`'s own generic per-row grouping interpreter itself, not fetch cost or arithmetic. `Scry.Core.Executor.try_aggregate_pushdown/6` computes eligibility and a `plan` itself and calls `aggregate/5` when an engine implements it; on decline (`:not_supported`) or ineligibility, falls straight through to exactly today's existing `GROUP BY` dispatch (streaming or eager), unchanged -- every engine that doesn't implement it (`Scry.Engine.ETS`, `Scry.Engine.InMemory`, `scry_test_time_series`) is completely unaffected.
  Researched and reviewed adversarially (two rounds, including empirical testing against a real SQLite database rather than assumed behavior) because SQL's own aggregate semantics genuinely diverge from Scry's: SQLite's `AVG()` always returns an inexact float (confirmed empirically), which would silently violate lang_spec §4's "exact rationals by default" promise -- **`avg` is excluded from pushdown eligibility entirely** in this version (a future increment could decompose it into a pushed `sum`+`count` pair recomposed via `Scry.Core.Rational.div/2` client-side, needing real `Executor`-side plan-rewrite/recomposition glue this version doesn't have). SQL's native aggregates also silently skip `NULL` values, where lang_spec §7 requires "aggregates over nullable fields hard-error -- no silent nil-skipping" (also confirmed empirically: a `NULL` row vanishes from `SUM`/`COUNT(col)`/`MIN`/`MAX`/`COUNT(DISTINCT col)` but not `COUNT(*)`) -- closed by requiring every aggregated column be schema-level `NOT NULL` before pushdown is trusted at all, an engine-side (`PRAGMA table_info`) concern.
  Eligibility (`Scry.Core.Executor.aggregate_pushdown_plan/3`) is deliberately narrower than the existing streaming-aggregation path's own eligibility: `group_mode: :plain`, no window function anywhere in the query, no `HAVING` (can reference an aggregate absent from `select` entirely -- its own separate, harder translation problem, deferred), no nested `SELECT` in `select`, never a correlated/nested query (`scope == []` -- resolving an ancestor-qualified `WHERE` reference into a literal before rendering SQL is deferred), a real (non-`WITH`-bound) source, every `group_bys` entry a single-segment path, every `select` item either a bare field exactly matching one of `group_bys` or a `sum`/`count`/`min`/`max` call (`count(distinct field)` included) over exactly one bare field.
  The engine's own raw per-group aggregate state flows into `finalize_agg/2` **completely unmodified** -- the exact same function the row-by-row streaming path already uses (`finalize_groups/6`, factored out of `grouped_base_rows_streaming/7` for this reuse, a pure, behavior-preserving refactor) -- so every aggregate's own exactness guarantee is enforced in exactly one place regardless of which path computed the raw pieces, not re-derived separately for pushdown.
  `test/scry/core/executor/aggregate_pushdown_test.exs`: an eligible query pushes down and never falls back to row-by-row computation; every eligibility exclusion (`avg`, `HAVING`, a window function, a nested `SELECT`, a non-`group_bys` field, `ROLLUP`/`CUBE`, a correlated/nested query) correctly declines and falls back; `:not_supported`/`{:error, _}` engine responses behave correctly (fall back vs. propagate); a flat aggregate over zero rows correctly reports `nil` (the engine's own `NULL`→`:empty` translation); a property test proving pushdown always matches the existing row-by-row streaming path for the same random data.

- `Scry.Core.Executor`'s streaming aggregation path (`sum`/`avg`/`count`/`min`/`max`, `group_mode: :plain`) now processes the fetched source in parallel: fixed-size batches (`config :scry_core, parallel_chunk_size: n`, default 5,000) run across a bounded pool of supervised worker tasks (`Scry.Core.TaskSupervisor`, `config :scry_core, parallel_max_concurrency: n`, default `System.schedulers_online()`), merged back in strict fetch order so the result -- representative row per group, first-appearance order, every running total -- is byte-identical to the single-process path it replaces, regardless of how many workers ran or in what order they finished. Measured motivation: `avg(age)` over 50,000 rows previously took ~58ms almost entirely in per-row map construction and aggregate evaluation (client-side, since Scry doesn't push aggregation into a backend's own query language) -- real, parallelizable CPU work once split into batches.
  `Task.Supervisor.async_stream_nolink/4` (a new `Scry.Core.Application`/`Scry.Core.TaskSupervisor`, `mix.exs` gains `mod: {Scry.Core.Application, []}`), not a linked task, is load-bearing: verified directly (a real crashing task, not assumed) that a linked task's own crash sends an uncatchable `EXIT` signal killing the calling process outright, which would have turned a query's own hard aggregate-nil error into an unrescuable crash instead of the ordinary, catchable exception it is today. `_nolink` preserves that -- a failing batch surfaces as a normal raise in whatever process called `Executor.run/4`, remaining batches never start once that happens, and the source `Cursor`'s own cleanup (`Stream.resource/3`'s `after_fun`) still runs either way -- all three confirmed directly, not assumed.
  `test/scry/core/executor/parallel_aggregation_test.exs`: correctness across chunk boundaries (flat and grouped aggregates, `count(distinct ...)` unioning across chunks, representative-row and first-appearance-order preservation, `HAVING`/`ORDER BY`/`LIMIT` composition, zero-row edge cases), a property test against an independent `Enum.group_by/2`-based reference, the hard-error/no-crash proof, and resource-cleanup-on-error proof.

- The chunk-and-ship parallel runner above generalizes into a shared `process_chunks_parallel/4` (batches via `chunk_stream/1`, dispatches via `Task.Supervisor.async_stream_nolink/4`, folds results via a caller-supplied `merge_fun` in strict fetch order) and gains a second caller: a plain `WHERE`+projection query (no `GROUP BY`, no window function, no `ORDER BY`, no `DISTINCT`) with no `LIMIT`, no nested `SELECT` anywhere in `select`, **and at least one real function call somewhere in `select`** now also processes its fetched rows in parallel (`run_plain_parallel/7`), reusing the exact same per-row `matches_all?/4`/`project_item/8` functions the sequential path already had. A `LIMIT`-bound query keeps using `run_plain_streaming/7` (early-stop beats splitting into chunks every one of which gets fully processed regardless); a query with a nested `SELECT` in `select` keeps using the existing sequential path (a nested query re-enters `Executor.run/4` per surviving row, and doing that inside an already-parallel worker would fan out unboundedly, since `Scry.Core.TaskSupervisor` has no `max_children` cap). The refactor is behavior-preserving by construction -- `test/scry/core/executor/parallel_aggregation_test.exs` passes unmodified against the generalized runner.
  The function-call requirement (`select_has_call?/1`) is itself a direct result of measuring, not assuming: a `select` of only bare field references turned out **~25-35% slower** through this new path than through the existing `run_plain_streaming/7` (measured on 200K- and 1M-row tables, at three different chunk sizes) -- every matching row still has to be copied into a worker's mailbox and back out again, and that copy cost outweighs a bare field access's own near-zero per-row compute. A `select` containing a real function call (`json(...)`, a `cast`, ...) is the opposite case -- **1.4-1.5x faster**, measured on the same tables with a `json(...)` decode + nested-path projection -- the per-row compute is now large enough to be worth parallelizing even after paying the same copy cost. `select_has_call?/1` gates on this directly rather than shipping a path that helps some queries and quietly regresses others.
  Fixed, as part of this work, a latent bug in the shared runner's own error handling (present since the aggregation path first shipped, but only exposed once a genuine BEAM-level runtime error -- not an explicit `raise` -- crashed a worker for the first time): `reduce_chunk_result/3` assumed a crashed task's exit reason always already carried a pre-built exception struct, true for `raise SomeException` but false for e.g. a failed function-clause match, whose raw exit reason is just an atom per `Task.Supervised`'s own `:error`-kind encoding -- that case fell through to a bare `exit/1`, silently defeating the entire point of using `async_stream_nolink/4` (an uncatchable crash instead of an ordinary, rescuable exception). Fixed by reconstructing the original failure's exact kind (`:error`/`:exit`/`:throw`) via `:erlang.raise/3` instead of assuming a struct is already there, letting ordinary `rescue`/`assert_raise` normalize it exactly as they would for code that never went through a `Task` at all.
  `test/scry/core/executor/parallel_plain_filter_test.exs`: correctness across chunk boundaries (a filter spanning many chunks against a hand-computed reference, exact row order preservation via a non-sorted comparison, `OFFSET` without `LIMIT`, a zero-match edge case, a nested-`SELECT` regression check), the hard-error/no-crash proof using the exact failure shape (`~` against a non-regex) that originally exposed the `reduce_chunk_result/3` bug, resource cleanup through the parallel path, and a property test against an independent `Enum.filter/2`+`Enum.map/2` reference.

- `Scry.Core.EngineBehaviour` gains an **optional** `fetch/4` callback -- `fetch/3` plus an `opts` hints map, currently carrying `opts.columns :: {:ok, MapSet.t(String.t())} | :unknown`, the exact top-level columns of a source a query references anywhere (`wheres`/`havings`/`group_bys`/`order_bys`/`select`), computed by `Scry.Core.Executor` itself (new public `referenced_top_level_fields/2`) and passed to whichever engine implements `fetch/4` -- preferred over `fetch/3` over `fetch/2`, same `function_exported?/3`-based, strictly additive posture `fetch/3` itself was introduced with. Motivated by a real, measured problem: a SQL-backed engine implementing only `fetch/2`/`fetch/3` always issues `SELECT * FROM table` and builds a full map per row regardless of how many columns a query actually needs -- for a `GROUP BY`/`WHERE` scan over a large table needing 2-3 of many columns, that's real, avoidable I/O and allocation before `Executor` does any actual work. `opts` is an open map (not a fixed parameter list) specifically so a previously-documented, still-unbuilt future extension (`{:param, name}`-pushdown, mentioned in this module's own moduledoc since `fetch/3` shipped) can add an `opts.params` key later without another signature change.
  `referenced_top_level_fields/2` is deliberately conservative: `:unknown` (fetch every column, today's exact behavior) whenever `select` has a nested `%Query{}` (no attempt to bubble a correlated reference up through nesting) or a window function (sidesteps window-function synthetic-field augmentation, which needs to append a key a fixed-shape compact row can't hold), built by reading `get_path_in/2`'s field lookup (`Map.get/2`, not `Map.fetch/2` -- a missing column silently becomes `nil`, never raises) as the correctness bar to clear, not assumed safe. Found and fixed before shipping, by an adversarial design review: a path's first segment is excluded as "belongs to an ancestor" only when the path has more than one segment -- `get_path/3`'s own single-segment clause never consults `scope` at all, so a bare single-segment path is always this query's own column, even if it happens to share a name with an ancestor.
  New `Scry.Core.Row` -- a compact, positional row (a shared column-index map, built once per fetch, paired with a values tuple) an engine may return from `fetch/4` instead of a per-row map. `get_path_in/2` (confirmed, by direct source audit, the *only* place in `Scry.Core.Executor` that reads a row's fields directly) gains two new clauses so a `Row` flows transparently through `WHERE`/`GROUP BY`/`ORDER BY`/`DISTINCT`/projection and correlated `scope` access (an ancestor's own row can itself be a `Row`) -- byte-identical output to the same query against plain-map rows, proven via a differential property test (same query, `fetch/4`-with-pruning vs. `fetch/2` baseline). `Row.fetch!/2` **raises** on a column outside its own index, a deliberate asymmetry from a plain map's silent `nil`-on-miss: since a `Row`'s index is built entirely from this feature's own column computation, a lookup miss can only mean the enumerator under-collected a genuinely-needed column -- a loud crash, not a silently wrong result.
  Every engine that only implements `fetch/2`/`fetch/3` -- `Scry.Engine.ETS`, `Scry.Engine.InMemory`, and the external `scry_test_time_series` package's own SQLite engine (which calls `Scry.Engine.Exqlite.fetch/2` directly) -- is completely unaffected. Aggregate/`GROUP BY` pushdown into a SQL engine's own query language, the single biggest remaining lever for a large `GROUP BY` specifically, is deliberately **not** attempted here: it needs an authoritative, not "trust but verify," engine contract, since `Executor` can't cheaply re-verify a `SUM`/`AVG` without redoing the computation -- separate, harder, future work.
  `test/scry/core/row_test.exs`, `test/scry/core/executor/referenced_top_level_fields_test.exs` (one test per `predicate()`/`expr()`/`body_item()` shape, mirroring `resolve_predicate_lhs/4`/`resolve_rhs/4`'s own clause sets one-for-one), and `test/scry/core/executor/fetch_hints_test.exs` (dispatch preference, `opts.columns` wiring, `Row` correctness through the full pipeline including a nested-`SELECT` correlation test where the *ancestor's* row is itself a `Row`, and the differential property test).

- `Scry.Core.Rational.add/2`/`sub/2`/`mul/2` gain a fast path for "both operands are already plain integers," skipping `new/2`'s own `Integer.gcd/2`-based reduction entirely -- an integer result there is always already in lowest terms, nothing for it to find. Measured motivation: profiling a `GROUP BY user_id`-style query (many distinct groups, one `sum(...)` accumulation per row) after the column-pruning/compact-row work above still found `Executor`'s own grouping ~8x slower than an equivalent native `Enum.reduce/3` over the same rows -- an isolated microbenchmark (`Rational.add/2` vs. native `+`, both over plain integers) found ~2x of that gap sitting in `Rational.add/2` alone, real, avoidable overhead on every single numeric aggregation in the system, not just this one query shape. `div/2` gets no equivalent fast path, deliberately -- `3/2` genuinely isn't an integer, so it always needs `new/2`'s own reduction to decide what the result actually is. The remaining gap (the generic per-row dispatch cost inherent to a tree-walking executor) is unaffected by this change -- aggregate/`GROUP BY` pushdown into a SQL engine's own query language remains the real fix for that, separate, larger, future work.
  `test/scry/core/rational_test.exs`'s existing property tests (which already generate plain-integer operand pairs as part of their normal random coverage) continued passing unmodified through this change -- proof it doesn't alter any observable result, only how it's computed -- plus a new, explicit property test asserting the fast path always agrees with the general `new/2`-based reduction path for every integer pair.

- `Scry.Core.EngineBehaviour` gains an **optional** `fetch/3` callback -- real, engine-side query pushdown, on top of the existing `fetch/2` contract, not a different one. Receives the whole `%Scry.Core.Query{}`, so an adapter backed by a real query language of its own (SQL, an ETS match spec, ...) can translate whatever it recognizes into a native, more efficient fetch instead of always returning every row for a source unfiltered. `Scry.Core.Executor.fetch_lazy/4` (`fetch_lazy/3` before this) prefers `fetch/3` via `function_exported?/3`, falling back to `fetch/2` otherwise -- every existing engine (both real `EngineBehaviour` implementations in this workspace, which only define `fetch/2`) keeps working completely unchanged; this is strictly additive and opt-in, not a breaking change.
  The load-bearing safety invariant, and it's asymmetric: `Scry.Core.Executor` makes zero assumptions about how much (or how correctly) a `fetch/3` implementation actually optimized -- it unconditionally re-applies its *entire* existing pipeline (`wheres`, grouping/aggregation, sorting, dedup, pagination, projection) to whatever comes back, exactly as it already does for `fetch/2`. An engine that *over-includes* (returns extra rows a correct pushdown would have excluded, or ignores `query` entirely) is always corrected downstream -- filtering an already-filtered set is idempotent. An engine that *under-includes* -- a buggy predicate translation that wrongly drops a row a correct fetch would have returned -- is **not** caught by anything, since `Executor` never sees the dropped row to compare against. `fetch/3` is a trust-the-engine-for-completeness, verify-the-engine-for-correctness-of-what-it-returns contract, not a fully-checked one -- stated plainly in `EngineBehaviour`'s own moduledoc, not left to be discovered the hard way.
  Scope boundary, also explicit: `fetch/3` may narrow *which* rows come back and in *what order*, but must still return the same row shape `fetch/2` would for that source -- never pre-aggregated/restructured data (that would require `Executor` to trust an engine's own aggregation logic outright, breaking the invariant above -- a real, separate, harder problem, not attempted here). Predicates referencing `{:param, name}` also aren't pushdown candidates in this version of the contract, since `params` isn't threaded into `fetch/3` -- a natural, non-breaking future extension (`fetch/4`), not a silently-papered-over gap.
  `test/scry_core/executor/lazy_execution_test.exs`'s new `"optional fetch/3 pushdown"` describe block adds a `PushdownEngine` fixture whose own `fetch/2` unconditionally raises, proving `fetch/3` is genuinely preferred whenever present; a `fetch/3` that genuinely narrows results, proving the optimization path's own output flows through correctly; and a `fetch/3` that deliberately over-includes (ignores `query.wheres` entirely), proving `Executor`'s final output is still exactly right -- empirical proof of the safety invariant, not just a design claim.

- A real `ORDER BY` combined with a real `LIMIT` (no `DISTINCT`, no window function, no `REQUIRED` nested `SELECT` directly in `select`) now streams with a *bounded* buffer instead of materializing and sorting the whole filtered row set -- `O(limit + offset)` memory, not `O(n)`, the same memory-boundedness goal the earlier `LIMIT`-only streaming path and streaming `GROUP BY` aggregation already deliver for their own cases. Every row still has to be pulled and compared against the buffer (there's no way to know a later row won't outrank a currently-buffered one without seeing it), so this bounds *memory*, not *time* -- consistent with this whole feature area's own "memory boundedness, not speed" goal from the start.
  New `ScryCore.Executor.run_topk_streaming/7`: maintains an always-sorted buffer of at most `limit + offset` rows (`insert_topk/5`/`insert_sorted/4`, reusing `sorts_before?/4` -- `sort_rows/3`'s own comparator -- directly, so the buffer's own final content is provably identical to a full `Enum.sort/2` truncated to the same size, not a separate ordering implementation that could disagree with it), then projects and paginates only that small final buffer. `DISTINCT`/a window function/a `REQUIRED` nested `SELECT` directly in `select` (`select_can_skip_rows?/1`) all still route to the existing, unchanged, fully-materializing `run_plain/8` -- a row `project_item/8` might still `:skip` can't safely be counted toward the bounded buffer's own capacity ahead of time, so that combination stays honestly narrower rather than silently under-producing (`"limit applies after REQUIRED drops rows, not before"`, an existing regression test, already proves this boundary holds).
  `test/scry_core/executor_test.exs`'s new `"bounded top-K streaming"` describe block covers ascending/descending sort + `LIMIT`, `LIMIT` + `OFFSET` together, `LIMIT 0`, stable tie-breaking, `DISTINCT` still forcing the eager path, and a property-based test (`stream_data`, since the input space -- arbitrary row sets, sort direction, limit, offset -- is exactly the kind this project already prefers property tests for) proving the result always matches a naive `Enum.sort/2` + `Enum.drop/2` + `Enum.take/2` reference implementation. `test/scry_core/executor/lazy_execution_test.exs` adds a step-counted proof that this path genuinely pulls *every* row (1000 of 1000, unlike the `LIMIT`-only path's own early stop at 503) -- confirming the "memory-bounded, not row-count-bounded" distinction empirically, not just by design intent.

- The *runtime* half of lang_spec.md §7's null-safety rule: "comparing a nullable field directly against a typed value is a hard error -- always at runtime." An ordinary comparison (`WHERE`/`WHEN`, and both the eager and streaming `HAVING` paths, kept in parity) now raises the moment either side of a `:cmp` resolves to `nil`, the same "no silent nil-skipping" rule this module's own aggregates already enforce -- previously a `nil` field just fell through to Erlang's own total term order (`nil > 30` quietly meaning something no query author intended, rather than erroring). One explicit exemption, matched ahead of the general rule: a literal `nil` on a comparison's own right-hand side (`field = nil`/`field != nil`, the only shape `KW_NIL` can ever produce) is lang_spec's own null-check idiom, never hard-erroring -- Elixir's own short-circuiting `and`/`or` (already how `{:and, ...}`/`{:or, ...}` are evaluated) is what makes both of §7's own worked examples (`WHERE NOT (age = nil) AND age > 30`, `WHERE age = nil OR age > 30`) flow-sensitively safe at runtime for free, no separate narrowing pass needed. A `WHEN` clause's own guard predicate hard-errors the same way for free too, since it already reuses `eval_predicate/4` directly.
  This is the runtime half only -- it needs no schema/registry, since it's about a row's own actual value, not a declared type. The *compile-time* half (rejecting an unguarded nullable-field comparison statically, wherever a schema is reachable) -- along with union-type comparison checking, the schema-registry hook, and `Json<Type>` field-access validation -- is real, separate, larger work still gated on `type_decls`/a registry existing at all, neither of which do yet (`ScryCore.Query`'s own moduledoc has the full scope reasoning).
  `test/scry_core/executor_test.exs`'s new `"null-safety (lang_spec.md §7)"` describe block covers an unguarded comparison hard-erroring, the `field = nil`/`field != nil` idiom never hard-erroring, both of §7's own worked flow-sensitive-guard examples (`AND`/`OR`), a `WHEN` clause's own guard, and the `HAVING` case through both the eager (forced via a `percentile` call elsewhere in `select`) and streaming grouped-aggregation paths.

Root cause: `@skip`-splicing only ever happens *between* two elements of a sequence, so trivia after the true final token of a top-level match was never consumed, and `Grammar.VM`'s own top-level match requires the entire token stream consumed. Fixed with a trailing `TRIVIA?` on `document` (the real root) -- confirmed empirically that it's the ordinary auto-splice inserted just *before* that trailing element doing the actual consuming, not `TRIVIA?` matching anything itself, so it adds no capture `ScryCore.Actions`' own `document` handler needs to account for. Found (not introduced) while writing the FRAGMENT feature's own multi-line test fixtures -- `select` alone had the identical gap before `document` became the root, just untested until then.
  The sibling gap that same investigation found -- `body_list`'s `COMMA` separator has no "a line break suffices" alternative yet (lang_spec §6) -- is *not* fixed here; it needs a dedicated `NEWLINE` token no longer folded into skip-trivia, a materially bigger change than this one-line addition (see `body_list`'s own grammar comment).

- `ScryCore.Executor`'s aggregate-detection family (`*_has_aggregate_call?`) now recurses into a call's own arguments, not just its outer name. Found as a real, pre-existing gap while implementing `count(distinct ...)`: a cast wrapping an aggregate with no explicit `GROUP BY` (`SELECT products { total: string(sum(price)) }`) never triggered grouped/flat-aggregate execution at all, since `string` itself isn't a real aggregate name, and instead hit the per-row rejection error a bare `sum(...)` alone already has for a genuinely per-row context -- confirmed empirically before fixing, not assumed. Not present before the explicit-casts feature gave a call something to nest an aggregate inside.

- Window functions -- `OVER [PARTITION BY ...] [ORDER BY ...] [ROWS BETWEEN <bound> AND <bound>]` (lang_spec.md §5.5), plus 4 new window-only built-ins: `row_number()`, `rank()`, `first_value(expr)`, `last_value(expr)` (§5.8). Every existing aggregate (`sum`/`avg`/`count`/`min`/`max`/`stddev_*`/`var_*`/`percentile`) is usable as a window function too (e.g. a running total). This closes lang_spec §5.8's entire built-in-function surface. Scoped to an **ungrouped** query only this increment -- combining a real `GROUP BY`/aggregate query with a window function in the same `SELECT` raises a clear, documented "not supported yet" error rather than being attempted; lang_spec's own worked example (§11: `SELECT employees { name, rank: row_number() OVER PARTITION BY department ORDER BY salary DESC }`) has no `GROUP BY`, confirming the ungrouped case is the load-bearing one.
  `priv/grammar.aether`: `call`'s own `call_args` is optional now (bare, unrenamed, per this file's own repeatedly-confirmed "renaming an optional rule reference produces a spurious second capture" finding) -- the first real need for a zero-argument call (`row_number()`/`rank()`). New `window_call := call:call KW_OVER over:over_spec`, tried before `call_with_path`/`call` in `primary` (same "more specific first, backtracks cleanly" pattern already proven there); `over_spec`'s own `partition_clause?`/`order_by_clause?`/`frame_clause?` reuse `field_list`/`order_by_clause` verbatim (the exact same shapes `GROUP BY`/top-level `ORDER BY` already use) rather than duplicating either rule. 9 new keywords (`OVER`/`PARTITION`/`ROWS`/`BETWEEN`/`PRECEDING`/`FOLLOWING`/`CURRENT`/`ROW`/`UNBOUNDED`), reusing `AND`/`BY` directly. All confirmed via scratch grammar before touching the real file.
  `Query.expr()` gains `{:window, call, partition_by, order_bys, frame}` -- `partition_by`/`order_bys` deliberately reuse `Query.t()`'s own `group_bys`/`order_bys` field *types* verbatim, no new type invented. Execution (`ScryCore.Executor`) needed no signature changes to `resolve_rhs/4` or any existing resolver: every window call in a query's own `select` is collected and replaced, in one pass, with a synthetic `{:field, ["0_scry_window_N"]}` reference (a leading-digit key, provably collision-proof with a real field name -- `field_name := IDENT | ESCAPED_IDENT` can never start with a digit) *before* projection; each window function's own value list is computed once (partition, sort each partition via the *existing* `sorts_before?/4`, compute per-row) and folded onto its own row under that same key, so `project_all`/`resolve_rhs` resolve what looks like an ordinary computed field, with zero awareness window functions exist at all. Confirmed structurally, not just by convention, that a window call can never reach `WHERE`/`HAVING`/`GROUP BY` in a valid parse tree in the first place (`predicate_lhs`/`in_lhs`/`comparison`'s own right-hand alternatives never reference `window_call`/`primary`), so no defensive rejection clauses were needed on any resolver.
  An aggregate used as a window function dispatches through the *existing* `eval_aggregate/5` directly, unmodified, over the row's own frame subset -- reusing 100% of its arity/nil-hard-error/`distinct`-rejection/`percentile`'s own 2-arg handling for free. `first_value`/`last_value` deliberately do **not** nil-hard-error (a documented distinction from the 10 aggregates-as-window-functions) -- they *select* one row's value rather than *reduce* many, so lang_spec's "no silent nil-skipping" rule (about a reduction dropping nulls) doesn't apply the same way. Default frame is the whole partition *regardless of whether `ORDER BY` is present* (lang_spec's own explicit "deliberately not SQL's behavior" rule -- confirmed with a test that would give a different, wrong answer under SQL's own implicit-cumulative-frame rule). `rank()` is tie-aware (equal `ORDER BY` keys share a rank, the next rank skips accordingly); an empty `ORDER BY` list makes every row vacuously tied, so `rank()` alone gives every row rank `1` with no special-casing.

- Extended standard aggregates -- `stddev_samp`, `stddev_pop`, `var_samp`, `var_pop`, `percentile(expr, p)` (lang_spec.md §5.8, "ANSI SQL:2003 forms" and "General ordered-set aggregate, `p ∈ [0,1]`"). All 5 join `@aggregate_names` and compose exactly like `sum`/`avg`/`count`/`min`/`max` already do -- flat-aggregate detection, `GROUP BY`/`HAVING`, the nil-hard-error rule, and the `distinct`-misuse rejection all apply uniformly, no special-casing needed at any of those levels.
  `var_pop`/`var_samp`/`stddev_pop`/`stddev_samp` stay in the exact-rational tower through the mean and sum-of-squared-deviations steps (`ScryCore.Rational.add/sub/mul/div`); only `stddev_*`'s own final square root needs `Rational.to_float/1` + `:math.sqrt/1`, since the rationals aren't closed under it (this module's own moduledoc already flagged `sqrt` as future work) -- the one place these 4 are ever inexact. `_samp` (Bessel's correction, `n - 1`) is `nil` below 2 data points, the same "no data, no crash" convention `sum`/`avg`/`min`/`max`'s own `[]` case already has for zero.
  `percentile(expr, p)` needed its own `eval_aggregate/5` clause, not the existing generic single-argument one -- the first standard aggregate that isn't 1-arity. `p` resolves once against the group's own representative row (`representative/1`, the same row a plain field on a predicate's own group-lhs already resolves against), not once per member row like `expr` is; its own out-of-range check runs before scanning `expr` at all. Implemented as a *discrete* order-statistic (nearest-rank: sort ascending via the existing `term_order/2`, pick the value at `ceil(p * n)`), not SQL's `percentile_cont` -- lang_spec's own "General ordered-set aggregate" framing (not "numeric aggregate") reads as wanting this to work over any `term_order/2`-orderable value (dates, strings), and only picking an actual value from the set (never interpolating between two) is well-defined for all of them uniformly. A clause-ordering bug was caught empirically before landing: `percentile`'s own arity-mismatch clause has to be declared *before* the generic single-argument `eval_aggregate` clause, or a wrong-arity `percentile(x)` call silently matches that generic clause instead and crashes inside `apply_aggregate/2` with an opaque `FunctionClauseError` rather than `percentile`'s own clear message.

No new dependency -- `json` is Erlang/OTP's own stdlib module (added in OTP 27; this project already targets OTP 28 per `.tool-versions`), decoding directly into a plain map with *string* keys, indistinguishable from row data once decoded.

  `ScryCore.Executor.eval_aggregate/5` dedupes (`Enum.uniq/1`) the resolved per-member-row values -- after the same nil hard-error every other aggregate operand already gets, no carve-out -- then counts. `DISTINCT` is syntactically permitted on *any* call's argument at the grammar level, not just `count`'s (the same "grammar stays permissive, execution rejects misuse" posture an unknown function name already has) -- `sum(distinct x)`/`string(distinct x)` parse, then raise a real, clear error at execution time (`eval_aggregate/5`'s own new clause; `resolve_rhs/4`/`resolve_group_rhs/4`'s own new `{:distinct, _}` rejection clauses respectively), never silently treated as a literal argument value.

- Explicit casts -- `string`/`int`/`exact`/`inexact` (lang_spec.md §5.8). No grammar changes needed -- `call`/`call_args` already parse any `identifier(args)` generically (built for the aggregate-function feature). `inexact(x)` is the one place a real native `float()` ever enters the pipeline, which required real, correctness-critical work beyond the 4 cast functions themselves:
  `ScryCore.Rational` gains `to_float/1`/`from_float/1` (`Float.ratio/1`, the exact IEEE-754 value of a double, always exists/bounded) and leading contagion clauses on `add/2`/`sub/2`/`mul/2`/`div/2`/`pow/2` -- lang_spec.md §4's own rule, *"mixing exact and inexact in one operation yields inexact"*: the moment either operand is a float, the whole operation happens in ordinary Kernel float arithmetic and returns a plain `float()`, never routed back through `new/2`. `compare/2` is deliberately **not** contagion the same way -- a float argument converts to *its own* exact value first, since a comparison result isn't a "value" contagion has anything to say about, and exact comparison is strictly more correct than comparing two lossy floats. `ScryCore.Executor.term_order/2`'s two `%Rational{}`-specific guards widen to accept a `float()` argument accordingly, closing a gap that module's own comment had flagged as real-but-unimplemented since the aggregate-function feature.
  `ScryCore.Executor.aggregate_query?/1`'s own call-detection (renamed `*_has_call?` → `*_has_aggregate_call?`) narrows from "any function call" to "a call to one of the 5 real aggregate names" -- a real, found-and-fixed bug this feature exposed: left unnarrowed, an ordinary `SELECT products { p: string(price) }` would have wrongly collapsed into a single flat-aggregate-shaped row instead of projecting one row per product, since no non-aggregate call existed before now to tell apart from an aggregate one. A shared `apply_cast/2` is called from all 4 places an `expr()`/predicate left-hand side gets resolved (the per-row and grouped paths alike), each already having resolved a cast's own arguments through *that call site's own* resolver first -- so a cast wrapping an aggregate (`string(sum(total))`) or a grouped field both compose correctly for free, via ordinary recursion.
  Cast value domain is Scry's own concrete value universe (exact numbers, floats, strings, booleans, nil, dates/timestamps, atoms), not arbitrary Elixir terms -- a value outside it raises a clear error rather than falling back to `inspect/1`-shaped text. `string(...)` renders a `%Rational{}` as `numerator/denominator` (the same shape it'd be written as a literal, not a lossy decimal -- `1/3` has no terminating decimal at all) and a date/timestamp via the exact ISO 8601 shape it was originally parsed from. `int(...)` truncates toward zero via exact integer division on a `%Rational{}`'s own parts, never a lossy float `trunc/1`, staying correct for arbitrarily large numerators/denominators.
  Found empirically while property-testing `to_float/1`/`from_float/1`'s own round-trip: `-0.0` and `0.0` are bit-distinct IEEE-754 values with no exact rational distinction between them (the rationals have no signed zero) -- `from_float(-0.0)` correctly produces plain exact `0`, confirmed as a real, documented edge case, not a defect.

- Duration/byte-size literals (lang_spec.md §4) -- `priv/grammar.aether`'s new `DURATION`/`BYTE_SIZE` tokens (`DIGIT+ ("." DIGIT+)? <unit>`), with the concrete unit vocabulary lang_spec.md itself previously only illustrated with two examples each: `ns`/`us`/`ms`/`s`/`m`/`h`/`d` for duration, decimal (SI) `B`/`KB`/`MB`/`GB`/`TB`/`PB` and binary (IEC 60027-2) `KiB`/`MiB`/`GiB`/`TiB`/`PiB` for byte size (mirrored in `lang_spec.md` itself, alongside this implementation). Every unit suffix is written `"unit"cs` -- Aether's own per-literal case-sensitivity override, forcing case-sensitivity for these tokens specifically despite this grammar's file-wide `@case_insensitive` pragma (confirmed empirically that `5M`/`5MS` correctly fail to parse rather than silently matching the wrong unit, matching real-world convention across Prometheus/Kubernetes/Go/AWS).
  Both collapse straight into the ordinary exact-rational tower, exactly like `RADIX` literals already do -- a canonical base unit (seconds for duration, bytes for byte size), not a distinct wrapped type: `500ms` is simply the exact value `1/2`, `1.5h` is exactly `5400`. `ScryCore.Actions`' own `handle_token` clauses split the token's raw text on the digit/letter boundary alone (unambiguous by construction, since the grammar's own token shape already guarantees digits and letters never mix) and multiply the parsed magnitude by the unit's own canonical value via `ScryCore.Rational.mul/2`.

- Query combinators -- `UNION`/`UNION ALL`/`INTERSECT`/`EXCEPT` (lang_spec.md §5.4, "Top-level, joining two complete select blocks"), the direct prerequisite for `WITH RECURSIVE` (§5.4.1, "`union`'s default dedup is what guarantees termination over cyclic data" -- itself still not implemented, needing its own fixpoint-iteration executor logic plus the graph variant's `VIA`). A new struct, `ScryCore.CombinedQuery` (`op`/`left`/`right`, `left`/`right` each `Query.t() | CombinedQuery.t()`), represents a combined result -- a real, separate top-level type from `%Query{}` rather than a field bolted onto it, since a chain of 3+ combinators is a binary tree and `Query.t()`'s own `source`/`wheres`/`select` fields have no way to mean "the result of two other queries combined." `ScryCore.parse/1` and `ScryCore.Executor.run/4` both widen their own `@spec`s to `Query.t() | CombinedQuery.t()` accordingly -- a backward-compatible widening, confirmed against every existing caller.
  `priv/grammar.aether`: `combined_select := head:select combinator_tail*`, folded **left-associative** in `ScryCore.Actions` (`fold_combinators/2`, mirroring `additive_tail`'s own proven fold shape) -- deliberately not naive right-recursion, which would silently give `EXCEPT`/`INTERSECT` chains the *wrong* grouping (`A EXCEPT (B EXCEPT C)` instead of the correct `(A EXCEPT B) EXCEPT C`, since neither operator is commutative), verified end-to-end, not just asserted. `combinator_tail`'s own first draft renamed the repeated rule reference (`tail:combinator_tail*`) and immediately hit the same "renaming produces a spurious raw-text capture" finding this session has run into repeatedly elsewhere -- caught empirically before it reached real code, fixed to the proven bare/unrenamed form.
  Combinators apply only at the very top of a document -- never inside a `WITH` binding's own value, never inside a nested `SELECT` body item (both still reference plain `select`, confirmed to be real, enforced parse errors, not just documented intent) -- which is what keeps `ScryCore.WithCycleCheck` completely untouched by this change: every `with_bindings` value stays exactly `Query.t()`. `ScryCore.FragmentResolver` gains one new clause resolving `...spread`s on *both* sides of a combinator. Execution (`ScryCore.Executor`): both sides run fully and independently through their own complete pipeline, then their row lists combine (`union`/`intersect`/`except`, not `_all`, dedupe their own result, standard SQL:1999 set semantics) -- no pushdown, no shared fetch, this module's existing "correct, not necessarily efficient" posture. Row membership for `intersect`/`except` uses ordinary `MapSet` structural equality, which has the same previously-undocumented `%DateTime{}`/`%NaiveDateTime{}` precision-mismatch gap `term_order/2`'s own comment already documents for *ordering* two such values -- found, not fixed, while writing this.

- `WITH <name> = SELECT ... { ... }` named reusable sub-queries (lang_spec.md §9, SQL CTE equivalent -- vs. `FRAGMENT`'s reusable *shape*, this is reusable *data*). `priv/grammar.aether`'s `document` root grows a second top-level declaration list (`document := fragment_decl* with_decl* select`, `with_decl := KW_WITH name:field_name EQ select:select`, reusing `select` directly for the bound value -- a `WITH` binding is a full query, its own `where`/`group by`/`having`/etc. all apply normally). `FRAGMENT`s must all precede any `WITH`s in the same document -- a narrower grammar than lang_spec technically allows (it never shows the two mixed either), not a spec violation, chosen to avoid a unified `top_level_decl := fragment_decl | with_decl` choice rule's own tag-dispatch complexity.
  Unlike a `FRAGMENT` spread, a `WITH` reference has no distinguishing sigil -- `SELECT active_users { name }` is syntactically identical whether `active_users` is a `WITH` binding or a real engine source, so resolution happens at *execution* time, not parse time: `ScryCore.Query.t()` gains a `with_bindings` field (meaningful only on the top-level query), and `ScryCore.Executor` intercepts any query whose own `source` is exactly `[name]` for a declared binding, running that binding (fresh, every time it's referenced -- no caching, the same "correct, not necessarily efficient" posture `REQUIRED`'s own re-fetch cost already has) instead of calling the real engine's `fetch/2`. `with_bindings` threads through every level of recursion unchanged, the same way `params` already does -- document-global, not scope-dependent, so a correlated nested `SELECT` several levels deep can reference a top-level `WITH` binding, and a `WITH` binding can itself reference another one, both verified end-to-end.
  A new module, `ScryCore.WithCycleCheck`, statically walks every binding's own dependency graph (its `source`, plus any nested `SELECT` body item's own `source`, recursively) before `ScryCore.parse/1` ever returns -- a `WITH` binding that (directly or transitively) references itself would otherwise make `ScryCore.Executor.run/3` recurse into itself forever the first time anything referenced it, a real infinite loop no `{:error, _}` return from execution could ever surface cleanly. Two duplicate-declaration checks (`{:duplicate_fragment, name}`/`{:duplicate_with, name}`) now share one helper in `ScryCore.Actions` (`build_name_map/2`), generalized from the `FRAGMENT`-only one this session's earlier feature added. `WITH RECURSIVE` (lang_spec.md §5.4.1) isn't part of this -- it needs `UNION`/`UNION ALL` (§5.4) to mean anything at all, and neither combinator is implemented anywhere in this codebase yet.

- Function-call syntax (`priv/grammar.aether`: `call := name:IDENT LPAREN args:call_args RPAREN`, wired into `primary` and a new `predicate_lhs := call | path` used everywhere `comparison` previously used a bare `left:path`) plus real execution for lang_spec.md §5.8's 5 standard aggregates -- `sum`/`avg`/`count`/`min`/`max` -- and `GROUP BY`/`HAVING` (§5.2), closing the last big piece of core §5 vocabulary `ScryCore.Executor` had parsed but never run. The rest of §5.8's built-in surface (casts, `json`, window functions, `count(distinct ...)`) stays deferred, same phased posture as everything else this codebase hasn't gotten to yet.
  `predicate_lhs` deliberately widens narrower than `Query.expr()` in full -- a bare field predicate still resolves to the exact same plain `[String.t()]` as before, so every existing test/predicate is unaffected; only the new `{:call, name, args}`-as-left-hand-side shape (needed for `HAVING sum(total) > 200`, lang_spec §11's own worked example) is new surface. The right-hand side is *not* widened the same way (`HAVING sum(a) > avg(b)` stays unsupported) -- the one concrete need is call-on-the-left-only.
  `ScryCore.Executor.run/5` splits into `run_plain/6` (today's original per-row pipeline, extracted verbatim -- provably unaffected for any query `aggregate_query?/1` says `false` for) and `run_grouped/6`. No explicit `GROUP BY` isn't a special case: `group_rows/3` returns one implicit group containing every filtered row when `group_bys` is empty, which is exactly the mechanism that makes §11's own nested, un-grouped `SELECT orders { count(id), sum(total) }` work -- a nested query is already executed recursively via the existing `%Query{}` body-item clause, so a flat aggregate inside a nested `SELECT` falls out for free, verified end-to-end (`executor_test.exs`'s own §11-shaped test), not just by inspection. *Any* function call at all (not just the 5 real aggregates) triggers the grouped path, so an unknown/unsupported function name still gets a clear error there instead of crashing on a `resolve_rhs` clause that was never written to expect `{:call, ...}`.
  Aggregates hard-error (`raise ArgumentError`) on encountering any `nil` operand, per lang_spec.md's own "Aggregates over nullable fields hard-error the same way [as comparing a nullable field directly] -- no silent nil-skipping; filter explicitly first" -- no special-cased null-skipping for `count`, unlike SQL's own `COUNT(column)`. `count([])` is `0`; `sum`/`avg`/`min`/`max` of `[]` are `nil` -- matching real SQL's own empty-aggregate answers, which is what makes a flat aggregate over zero filtered rows still produce exactly one well-defined output row. A grouped/aggregate query's own output sorts *after* projection (unlike the plain per-row path, which sorts before, specifically so `order_by` can reference a field outside the projected shape) -- fully reusing `sort_rows`/`sorts_before?`/`get_path` unchanged, since there's no such "outside the shape" source row left once grouping has collapsed multiple rows into one.
  A `GROUP BY`'s own group context is just its member rows, never a separately tracked key map -- a plain field resolves against the group's first member row (every member of a well-formed group already carries the identical value for any field that's actually a `GROUP BY` field), the same "not enforced, but well-defined" posture this module already has for a non-grouped `order_by`/`distinct` field. A nested `SELECT`/conditional field/`:variant` body item inside a grouped query's own `select` is a clear `{:error, {:unsupported_grouped_body_item, item}}`, not supported this increment.

- `priv/grammar.aether`: `FRAGMENT <name> { <body-item> ... }` declarations and `...<fragment-name>` spread (lang_spec.md §5.11/§9, GraphQL-style reusable *shape*). The grammar's own root changes from `select` to a new `document := fragment_decl* select` -- a query text is now zero or more top-level `FRAGMENT`s followed by exactly one `SELECT`, provably a no-op for every existing single-`SELECT` query (`fragment_decl*` is bare/unrenamed, confirmed empirically to always produce its own capture key -- `[]`, not a missing one -- when no `FRAGMENT` is present, the same finding `additive_tail*`/`when_clause+` already established). `SPREAD` (`"..."`, three literal dots) is unambiguous against the existing `DOT` token by ordinary maximal munch, the same way `POW`/`STAR` already coexist.
  A spread parses to a transient `{:spread, name}` placeholder (`ScryCore.Actions`) that never reaches `Query.body_item()`'s own public type -- a new module, `ScryCore.FragmentResolver`, expands every one in place (recursively, including inside a nested `SELECT`, and including a `FRAGMENT` that itself spreads another `FRAGMENT`) before `ScryCore.parse/1` returns, memoizing each fragment's own expansion so one referenced from more than one place is only ever walked once. Three real compile errors, each a plain `{:error, reason}` tuple (this module's own established convention, not a wrapped `%Ichor.Error{}`): `{:undefined_fragment, name}` (a spread names a `FRAGMENT` that was never declared), `{:fragment_cycle, [name, ...]}` (a `FRAGMENT` spreads itself, directly or transitively -- a real compile error, not a runtime concern, since a spread is pure textual substitution with no step in between to make a cycle merely expensive instead of infinite), and `{:duplicate_fragment, name}` (two top-level `FRAGMENT`s sharing a name, caught in `ScryCore.Actions` before the map ever reaches the resolver).
  Found while writing this feature's own multi-line test fixtures: `body_list`'s `COMMA` separator is unconditionally required today, with no "a line break suffices" alternative yet (lang_spec §6's own text) -- see the `### Fixed` entry below for the sibling gap this same investigation found (trailing trivia after a query's own closing `RBRACE`), which is fixed now.

- `priv/grammar.aether`: `WHEN <predicate> THEN <expr> [...] ELSE <expr>` conditional expressions (lang_spec.md §5.6/§9). Just another `primary` alternative, not a separate top-level-only construct -- lang_spec §9's own framing ("any body item may be an arbitrary expression") makes a `WHEN` conceptually the same kind of thing as any other expression, so it composes the same way (nests inside arithmetic, parentheses, or another `WHEN`'s own branches, e.g. `price * (WHEN vip = true THEN 1 ELSE 2)` -- no `END` keyword, lang_spec's own grammar has none; the closing paren from the *outer* expression is what naturally terminates it). `when_clause+` (one-or-more, verified to carry the same "renaming produces a spurious capture" finding `*` already has) puts "at least one WHEN...THEN" directly in the grammar; `ELSE` is mandatory the same way, no default.
  Each `WHEN`'s own condition reuses `predicate()` directly (the exact AST a `WHERE` clause already produces), so a `WHEN` condition can already do anything `WHERE` can -- comparisons, `and`/`or`/`not`, `in [...]`, `~`, correlation, external parameters -- for free. `ScryCore.Executor.resolve_rhs/4` gains a `{:when, clauses, else_expr}` clause that walks `clauses` in order via `Enum.find/2`, reusing `eval_predicate/4` directly on each condition (the same function `where` filtering already uses) and resolving the first match's own expression, falling through to `else_expr` when nothing matches.

- `priv/grammar.aether`: arithmetic expressions (`+ - * ** /`, lang_spec.md §5.10) and computed/aliased body items (`SELECT orders { subtotal: price * quantity }`, the exact worked example from lang_spec.md §9). Standard precedence climbing (additive < multiplicative < power < primary), `**` right-associative. No function calls yet (`sum(...)` etc., §5.8) -- those are aggregate functions tied to `group by`/`having`, neither executed anywhere in this codebase yet either, so a separate, later increment.
  Each binary precedence level uses a *dedicated* tail rule (`additive_tail`, `mult_tail`), not an inline `(op:(...) right:...)*` group -- found empirically to matter, not a style choice: naming a choice group directly inside an inline *repeated* group scrambles the captures (the per-repetition `op`/`right` correlation is lost entirely; the individual token alternatives end up as separate, flat, disconnected lists at the outer rule's level instead). Wrapping each repeated element in its own named rule sidesteps this completely, confirmed with a scratch grammar before committing to either shape.
  `<alias>: <expression>` requires whitespace immediately after the colon -- also confirmed empirically, not a style nicety: `subtotal:price` (no space) tokenizes as `IDENT("subtotal")` + `ATOM(":price")` instead of alias+colon+expression, since maximal munch always prefers `ATOM`'s longer match whenever `:` is immediately followed by an identifier character. The worked example's own spacing (`subtotal: price * quantity`) already avoids this.
  `ScryCore.Rational` gains `add/2`/`sub/2`/`mul/2`/`div/2`/`pow/2`, all built on the existing `new/2`'s construct-and-reduce so the same exactness/collapse-to-integer guarantees apply automatically to every arithmetic result, not just literals. `pow/2` requires an **integer** exponent (lang_spec §5.10's own constraint -- the rationals aren't closed under an arbitrary rational exponent) and raises a clear `ArgumentError` for a non-integer one rather than a bare `FunctionClauseError`, since a non-integer exponent is syntactically reachable (`2 ** (1/2)` parses fine) even though semantically disallowed.
  `ScryCore.Executor.resolve_rhs/4` gains an `{:arith, op, left, right}` clause, recursing through both operands via itself (an expression is a tree of the same `{:field, ...}`/`{:param, ...}`/literal leaves a predicate's own right-hand side already resolves) and always routing through `ScryCore.Rational`'s functions, never Kernel `+ - * /` directly, so a whole expression chain stays exact throughout. A computed field composes with correlation and external parameters for free, since it reuses the exact same scope-aware `resolve_rhs/4` everything else already goes through.

- `priv/grammar.aether`: conditional field inclusion (`SELECT users { name, email IF $includeEmail }`, lang_spec.md §5.3/§9, the GraphQL `@include`/`@skip` equivalent), built directly on external parameters above. `body_item`'s plain-field alternative (`field_body_item := field:path if_clause?`) now optionally carries an `IF $<param>` suffix -- always a param reference specifically, per lang_spec's own grammar, not a general boolean expression (there's no general expression grammar to reference one from yet anyway). Produces `{:field, path}` unconditionally (unchanged) or `{:field, path, {:param, name}}` when written with `IF`. `ScryCore.Executor` resolves the condition the same way any other `{:param, name}` reference does (`resolve_rhs/4`) and, when falsy (`nil`/`false` -- Scry's own two falsy values, no implicit coercion of anything else), omits the key from the projected row entirely -- a genuinely absent key (`Map.has_key?/2` false), not a `nil`-valued one, matching GraphQL's own directive semantics. Needed a new `project`/`project_all` outcome, `:omit`, distinct from the existing `:skip` (`REQUIRED`'s own outcome, which drops the *entire* row) -- `:omit` only drops this one item's own key and continues projecting the rest of the row normally.
- `priv/grammar.aether`: external parameters (`WHERE age > $minAge`, lang_spec.md §5.7/§9) -- a new `PARAM` token (`$` + identifier-shaped text), added to `literal`'s own alternatives so it's usable anywhere a literal is, including inside an `in [...]` list. Parses to the placeholder `{:param, name}` (`ScryCore.Actions`) -- never resolved at parse time, since the whole point (per lang_spec's own framing) is a real injection-safety property: the actual value is supplied separately, out of band, never string-interpolated into query text. `ScryCore.Executor.run/4` gains a `params` argument (default `%{}`, so every existing 3-arity call site -- including `scry_test_engine_core`'s own -- is unaffected) resolving `{:param, name}` wherever it appears, reusing the same `resolve_rhs/4` a field-to-field comparison's right-hand side already goes through. A query referencing a name absent from `params` raises `ArgumentError` rather than returning `{:error, _}` -- deliberate: `run/3`'s own `@spec` promises exactly two outcomes, and threading a third failure mode through the `where`-filtering `Enum.filter` would need the same `Enum.reduce_while` restructuring `project`/`project_all` already have for a different reason, for what's a caller-supplied-insufficient-input class of error, not a data-shaped one -- consistent with this module's existing posture elsewhere (a type mismatch, `~` against a non-string, already raises rather than returning `{:error, _}`).
- `priv/grammar.aether`: nested `SELECT` as Scry's SQL-JOIN equivalent, correlated (lang_spec.md §6, "Correlation and joins") -- a nested query's own `WHERE` can now reference an *enclosing* query's row via the field-to-field comparison mechanism above (`WHERE user_id = users.id`), and a new `REQUIRED` modifier (bare keyword, end of `select`'s header-modifier chain -- a different kind of modifier than the six before it, since it's read by the *parent's* projection step after this query's own pipeline has already finished, not evaluated as a step of this query's own) drops the enclosing row when the nested collection comes back empty (INNER-JOIN-like), vs. today's existing default of keeping it regardless (LEFT-JOIN-like). Only these two states -- RIGHT/FULL OUTER JOIN aren't expressible, deliberately: both need a flat row with nulls standing in for a missing side, and Scry's nested output has no equivalent shape.
  Qualified-path resolution: a path's first segment, if it matches an *ancestor* `select`'s own source name, resolves against that ancestor's row (nearest enclosing match first, arbitrarily many levels up -- proven with a grandchild-references-grandparent test, not just one level). Deliberately **no self-qualification** -- a path matching the *current* query's own source name is not specially stripped, since that would silently reinterpret ordinary nested-field access as same-row access whenever a row happens to contain a field named after its own source's tail segment. This keeps a non-nested `run/3` call provably unaffected (an empty scope chain makes the new lookup a strict no-op), confirmed by the full pre-existing test suite passing completely unmodified against the rewrite.
  `ScryCore.Executor` threads a `scope` (an ancestor `{name, row}` list) through `get_path`/`eval_predicate`/`sort_rows`/`project_all`/`project`/`project_item`; the public `run/3` is unchanged in signature and behavior, delegating to a new private `run/4`. Dropping a `REQUIRED`-empty row required a new third outcome (`:skip`, alongside `{:ok, _}`/`{:error, _}`) threaded through `project`/`project_all`'s `Enum.reduce_while` -- `project` halts on the first `:skip` (no reason to evaluate further body items for an already-dropped row; this also gives correct AND-semantics for free across multiple `REQUIRED` children on the same row), `project_all` excludes just that one row and continues. Verified empirically, not just reasoned through, that `LIMIT` correctly counts *surviving* rows rather than raw sorted ones (a test where sorting puts a to-be-dropped row inside the limit window, which a "limit before drop" implementation would get wrong and this doesn't).
  Cost, documented explicitly rather than left implicit: a correlated `REQUIRED` nested query is re-fetched in full (no pushdown, `EngineBehaviour`'s own existing limitation) once per *surviving* outer row, since `limit` only applies after projection -- not a new cost class (an uncorrelated nested query already re-runs redundantly per row today), but correlation is exactly what makes this matter at real row counts.
- `priv/grammar.aether`: field-to-field comparison (`WHERE price > cost`, lang_spec.md §5.9) -- a new `right_field:path` alternative on `comparison`, distinguished from the existing `right:literal` by capture-key name, the same proven pattern already used to tell `comparison`'s `in` alternative apart from the literal one. Lexically unambiguous (`literal`'s own alternatives never start with a plain `IDENT`/`ESCAPED_IDENT` the way `path` does), so no ordering sensitivity between the two `right*` alternatives. Produces `{:cmp, op, path, {:field, right_path}}`, reusing the `{:field, path}` tag `Query.body_item/0` already uses for a projected field -- structurally identical in both places, now genuinely two conceptually distinct positions for the same tag (documented in `Query`'s own moduledoc). `ScryCore.Executor.eval_predicate/2`'s two prior `{:cmp, ...}` clauses (one `:match`-specific, one generic) collapse into one resolve-then-dispatch shape (`resolve_rhs/2`), which also closes a real gap the naive addition would've reopened: `WHERE name ~ some_field` where the field resolves to a non-regex now hits the exact same documented, deliberate `Regex.match?/2` crash a non-string left-hand value already gets, not a fresh, undocumented `FunctionClauseError` from `ordering_result(:match, _)`. This is also the mechanism a nested `SELECT` will use to correlate to an enclosing row -- a separate, subsequent change (`ScryCore.Executor`'s own "not correlated" limitation, still true as of this entry).
- `priv/grammar.aether`: regex sigil literals (`@r/^[a-z]+@/`, lang_spec.md §4) paired with the `~` regex-match comparison operator (§5.9). `SIGIL` supports `/` as the only delimiter for now, not lang_spec's stated "any delimiter" -- a genuinely separate technical limitation from the deferred `;` block comment, and documented the same way: matching whatever character was chosen as the *opening* delimiter again at the close is a backreference, which neither Aether's native token primitives nor its own regex-sigil desugaring support (the latter explicitly rejects `\1`-`\9`). Real "any delimiter" support needs Aether's `@native`/`CustomLexeme` escape hatch, not investigated yet. Tag is a single letter (lang_spec gives exactly one, `r`) rather than an arbitrary-length name, to avoid designing for a second tag that doesn't exist yet. `ScryCore.Actions` compiles the `r` tag to a real `%Regex{}` via `Regex.compile/1` (a genuinely malformed pattern surfaces as an ordinary parse error, same `{:error, _}`-propagation pattern `DATE` already established) and rejects any other tag explicitly rather than guessing at unspecified semantics. `\/ ` inside sigil content is the one recognized escape (for a literal `/` without ending the sigil) -- deliberately not routed through `STRING`'s own `unescape/1`, since sigil content is regex syntax where `\d`/`\s`/etc. must reach the regex engine completely unmodified. `ScryCore.Executor` dispatches `{:cmp, :match, path, regex}` straight to `Regex.match?/2`, bypassing `term_order/2` entirely -- a regex match isn't an ordering comparison. A testing-methodology finding worth recording since it's easy to trip over again: two separately-compiled `%Regex{}` values from *identical* source text are not `==` (confirmed empirically -- the struct's `:re_pattern` field, an opaque compiled NIF resource, differs even then), so this file's own tests assert on `.source` rather than the whole struct.
- `ScryCore.Executor.run/3` now applies `distinct`/`order_bys`/`limit`/`offset`, not just `where`/`select` -- the pipeline lang_spec.md §6's own "Modifier ordering" paragraph describes: filter, sort (`order_bys`, evaluated against each *source* row, before projection -- the only reading consistent with §5.2's "ordering by a field outside the projected shape ... is a compile-time error" actually being possible to violate in the first place), project, dedupe (`distinct`, the projected output shape per §6's "Deduplication semantics", first-occurrence-wins via `Enum.uniq/1`), then paginate. Multi-key `order_bys` breaks ties left to right; the whole sort is stable (`Enum.sort/2`'s documented guarantee, verified empirically rather than just cited), so `distinct`'s own first-occurrence dedup after sorting is deterministic. The §5.2 compile-time error itself is **not** enforced -- no static validation pass exists anywhere in this codebase yet (the same gap `having`'s own aggregate-expression requirement has); this still produces a well-defined result for that case, just doesn't reject it. `group_by`/`having` remain the one real gap left in `run/3` -- they need aggregate-*expression* evaluation, which doesn't exist in the grammar at all yet.
- `priv/grammar.aether`: ISO 8601 date/timestamp literals (`2026-01-01T14:00:00Z`, lang_spec.md §4). `DATE`'s own token pattern is lexically permissive by design -- real calendar validation happens in `ScryCore.Actions` via `Date`/`NaiveDateTime`/`DateTime.from_iso8601/1` (tried most-specific-first), not hand-rolled in the grammar; a genuinely invalid calendar date (`2026-02-30`) surfaces as an ordinary `{:error, _}` parse result, confirmed empirically (a scratch grammar) that `handle_token/3` returning an error actually propagates correctly before relying on it, since every prior token handler had only ever returned `{:ok, _}`. Deliberately not attempting duration/byte-size literals in the same pass -- unlike ISO 8601, lang_spec.md gives no unit vocabulary for either, so implementing them means inventing one first.
- `priv/grammar.aether`: triple-quoted multiline strings (`"""..."""`, lang_spec.md §4). lang_spec.md specifies only the delimiter, nothing about escape or indentation-stripping behavior -- implemented as the most conservative reading available: content captured verbatim (embedded newlines included, no leading-whitespace stripping the way e.g. Elixir's own heredocs do), honoring the same `ESCAPE` token as the two single-line string forms for consistency. Disambiguated from a pair of adjacent empty `STRING` tokens by the same maximal-munch mechanics already relied on elsewhere in this file (`"""..."""` is strictly longer than whatever `STRING` alone could match from the same starting `"`).
- `priv/grammar.aether`: atom literals (`:active`, lang_spec.md §4) -- a new `ATOM` token, colon-*prefixed* per lang_spec.md §5.3's own distinction from the still-deferred colon-*suffixed* alias syntax (`subtotal:`), never subject to `@refine` (a wholly separate token from `IDENT`). `ScryCore.Actions` represents the value as `{:atom, name}` (a tagged binary), deliberately **not** a real Elixir atom via `String.to_atom/1` -- query text is arbitrary external input, and BEAM atoms are never garbage collected, so turning unbounded attacker-controlled text into new atoms one at a time is a genuine atom-table-exhaustion DoS vector, not a hypothetical one avoided for style. The atom's own text case is preserved as-is (no downcasing, unlike keyword reclassification) since there's no keyword-collision concern for a token `@refine` never touches.
- `priv/grammar.aether`: list literals (`[1, 2, 3]`), usable as a `literal` anywhere one is valid, not just inside `in [...]` -- a new `list` rule (`LBRACK items:literal_list? RBRACK`) that `in`'s own right-hand side now delegates to as well, replacing its previous inline `LBRACK literal_list? RBRACK` duplication. Recurses (a list of lists parses fine) via ordinary PEG recursion, not left-recursive since `list` starts with the `LBRACK` token rather than `literal` itself. Structural equality (`[1,2,3] = [1,2,3]`, lang_spec.md §4) needed no `ScryCore.Executor` change -- Elixir's own `==` is already structural for lists.
- `priv/grammar.aether`: backtick-escaped identifiers (`` `select` ``, lang_spec.md §3) -- a new `ESCAPED_IDENT` token, entirely separate from `IDENT` and so never subject to `@refine`'s keyword reclassification no matter what text it contains, letting a field/source name that happens to collide with a keyword (including one of this file's own recently-added `group`/`order`/... ) be written at all. `path`'s `head`/`tail` now reference a new `field_name := IDENT | ESCAPED_IDENT` rule instead of bare `IDENT` directly.
- `priv/grammar.aether`: single-quoted strings (`'...'`), alongside the existing double-quoted form -- lang_spec.md §4's own rationale for having two delimiters ("pick to avoid escaping").
- `priv/grammar.aether`: the full lang_spec.md §5.2 `select` header-modifier chain, in its required fixed order -- `group by <field>[, ...]`, `having <predicate>`, `distinct`, `order by <field> [desc|asc][, ...]`, and `limit <n> [offset <n>]`, alongside the existing `where`. `ScryCore.Query`'s `group_bys`/`havings`/`distinct`/`order_bys`/`limit`/`offset` fields (already shaped for this, impl_spec.md §7) are now genuinely populated by `ScryCore.Actions`, not just reserved. New keywords (`group`/`by`/`having`/`distinct`/`order`/`limit`/`offset`/`desc`/`asc`) reclassified case-insensitively the same way as every other core keyword. `group by ... rollup`/`... cube` and the "having requires an aggregate expression" compile-time check are still deferred (documented in the grammar file's own header) -- the fixed-order requirement itself is enforced by the grammar's own rule structure, not a separate check, and is tested as such (writing modifiers out of order fails to parse).

- `ScryCore.GrammarCompose.merge/2`: the core+fragment grammar merge from impl_spec.md §4 -- collision-checked (structurally-identical shared redeclarations, e.g. `TRIVIA`, are not collisions), with a proactive check that a fragment's `@skip` matches core's own (a fragment defaulting to a different skip token bakes an unmatchable reference into its own rules once merged -- found by actually running the composition, not assumed from reading Ichor's source).

- `ScryCore.Query`: the shared struct both Scry front ends (text grammar, and the not-yet-implemented Elixir-native builder, impl_spec.md §7) converge on.
- `ScryCore.Actions`: turns `priv/grammar.aether`'s parse tree into `%ScryCore.Query{}` -- covers everything the current Phase 1 grammar can produce (`select`/`where`/boolean logic/comparisons/`in`/dotted paths/projected fields), with core-only handling for the EP1(a) extension point (stored unexamined under `variant.select_ep1a`, a stand-in for real composed-Actions dispatch once a second real kind exists to compose against).
- `priv/grammar.aether`: `body_list` now accepts a nested `SELECT` (ordinary PEG recursion, no extension point needed) or a kind-contributed body item, not just a plain field -- a new `body_item_ep1` extension point (EP1(b)/(c)/(d): block-opening constructs, scoped pseudo-fields, value pseudo-fields), the union-capable kind introduced for `select_ep1a` below. Validated end to end with a fake `VIA edge { body }`-shaped fragment (`ScryCore.GrammarComposeTest`) whose own inner body recurses back into core's real `body_list`, not a fragment-local copy of it -- the actual point of testing an EP1(b) shape specifically, since EP1(a) never had to compose with anything of core's own.
- `Query.select` entries are now tagged (`{:field, path}` | a nested `%Query{}` directly | `{:variant, term()}`) instead of bare paths, to make room for the two new shapes above.
- `ScryCore.EngineBehaviour`: the shared execution scaffold every kind's own engine behaviour builds on top of -- one callback (`fetch/2`, fetch every row for a source; no pushdown yet, see the module's own moduledoc) for what an adapter actually has to supply, since filtering/projecting are core's own job.
- `ScryCore.Executor`: kind-agnostic query execution against any `ScryCore.EngineBehaviour` implementation -- filters via `wheres` (all six comparisons, `and`/`or`/`not`, `in`), projects `select` (plain fields, nested `SELECT`s run independently -- Phase 1's grammar has no correlation syntax yet, so every outer row gets the identical nested result, a real and documented limitation, not a bug), and returns an explicit error for a `:variant` body item, since core has no execution semantics for a kind-specific construct it doesn't know about. First real validation that a `%ScryCore.Query{}` can actually be *executed*, not just built -- the whole pipeline had only ever been proven up to "text → AST" before this.
- `ScryCore.parse/1`: the intended public entry point for anything outside this package -- parses query text straight to `{:ok, %ScryCore.Query{}}` using `ScryCore.Grammar.compile/0` (core's own grammar, recompiled from source each call -- no `mix ichor.gen`-equivalent Mix task exists yet, impl_spec.md §4) plus `ScryCore.Actions`, so a downstream package (`scry_test_engine_core`, next) never has to know `Aether.Parser`/`Grammar.Analysis`/`Grammar.VM` exist.
- `ScryCore.Rational`: exact rationals (lang_spec.md §4's "Numbers: exact rationals by default"), scoped to exactly what a literal needs -- `new/2` (GCD-reduced, sign normalized to the numerator, collapsing to a plain `integer()` when the reduced denominator is `1`, so the struct only ever represents a genuinely non-integer value) and `compare/2` (exact cross-multiplication, never a float). Property-tested (`stream_data`) against an independent cross-multiplication oracle restated from scratch, not calling back into the module under test. Deliberately not full arithmetic (`+ - * ** /` as an expression, `sqrt` exactness recovery, float-on-ingest conversion) -- nothing in the grammar can construct or evaluate an arithmetic expression yet, only a literal; see the module's own moduledoc.
- `priv/grammar.aether`: decimal (`3.14`), `2/3`-shaped rational, and radix (`0x1F`/`0o17`/`0b101`) number literals, alongside the existing bare-integer form -- `NUMBER` split into three mutually-exclusive tokens (`INTEGER`/`DECIMAL`/`RADIX`), disambiguated by Aether's own maximal-munch lexer rule alone (verified against Ichor's real tokenizer source, both the interpreted `Grammar.VM` and native-codegen paths, not assumed from documentation), plus a new `rational` rule (`INTEGER SLASH INTEGER`, ordered before bare `INTEGER` in `literal`'s own choice -- safe via ordinary PEG backtracking, not a genuine ambiguity). `ScryCore.Actions` parses `DECIMAL` text directly to its exact rational value (`3.14` → `157/50`, matching lang_spec.md's own worked example) and `RADIX` text via `String.to_integer/2`'s base argument -- both enter "the ordinary exact-rational tower... not a distinct type" (lang_spec.md §4), same as a plain integer literal.
- `ScryCore.Executor`: comparisons now dispatch through `ScryCore.Rational.compare/2` whenever either side of a `{:cmp, ...}` predicate is a `%ScryCore.Rational{}` -- Kernel's `< > <= >=` order a struct by raw field values, not by the fraction it represents, so `1/2 < 2/3` needs real numeric comparison, not the struct's own field ordering. A row's own field value only gets this treatment when it's already a plain `integer()`; a native Elixir `float()` there isn't covered (lang_spec.md §4's "conversion on ingest" model has no adapter-facing hook yet -- a real, separate, still-open gap).

### Changed

- `ScryCore.Executor`'s `compare/3` is now built on a shared `term_order/2` (returning `:lt`/`:eq`/`:gt`, same shape `Rational.compare/2`/`DateTime.compare/2`/`NaiveDateTime.compare/2` already return) instead of six independent op-specific clauses each redoing Kernel `== != < > <= >=`. Purely a refactor of `compare/3` itself -- no behavior change for any value type, verified by the existing predicate test suite passing unmodified -- but it's what let `order_by`'s new sort comparator (`sorts_before?/3`) reuse the exact same "how do we order any of our value types" logic the `where`-clause comparisons already had, rather than risk a second, subtly inconsistent implementation.
- **`select_ep1a` is no longer "exactly one fragment may define this rule."** lang_spec.md §5.2 itself has `last` (time-series) and `deep` (document) nominating the same header-modifier position, and a build can legitimately load both kinds at once -- treating a second fragment's contribution as a collision would make that combination impossible. `priv/grammar.aether` now gives `select_ep1a` a real default (`NEVER := []`, an empty character class that always fails -- not a `!`-negated lookahead, which turns out to mean "always succeeds with zero width" instead, confirmed empirically), and `ScryCore.GrammarCompose.merge/2` unions every loaded fragment's contribution into one `Choice` (deduplicating an exact repeat) for any rule name in its own `extension_points/0`, rather than requiring identity across every merge. A consequence worth calling out on its own: core alone now genuinely passes `Grammar.Analysis` (a zero-kind build, e.g. `scry_relational` alone, needs a working parser too) -- the "core alone fails, extension points are dangling references" property from the first version of this file was true only of that earlier, narrower design, not a property the architecture actually needs.

### Fixed

- `priv/grammar.aether`: `IDENT`/`ESCAPED_IDENT`/`ATOM`/`PARAM` no longer accept a bare `-` as an identifier-continuation character. lang_spec.md §3's own "Identifiers" section says only "Bare by default (`name`, `orders.total`)" -- it never mentions hyphens, and allowing them was an unjustified overreach from this file's own first draft. Found while scoping arithmetic operators: with `-` in `IDENT`'s own character class, maximal munch would read `price-quantity` as a single identifier, never as `price` `MINUS` `quantity` -- silently making subtraction impossible to write without spaces around it. No existing test relied on a hyphenated identifier (checked before fixing, not assumed), and a new regression test confirms `some-field` in a body item now fails to parse instead of silently meaning something else.
- `mix.exs`: `ichor` is now `only: [:dev, :test]`, not just `:dev` -- scry_core's own test suite drives grammar composition directly (unlike an ordinary consuming application, which only needs `ichor` at its own dev-time `mix ichor.gen` step) and genuinely needs the compiler present under `MIX_ENV=test`.
- `mix.exs`: added `:ichor` to `dialyzer: [plt_add_apps: ...]` -- Dialyzer's PLT auto-discovery respects `runtime: false` the same way a real release does, so it silently excluded `ichor` (and every `Aether.Grammar.t()`/`Ichor.TokenRefiner` type `ScryCore.GrammarCompose` references) without this.
- `mix.exs`: `ichor` is now a real (unscoped) dependency, not `only: [:dev, :test]` -- confirmed the hard way, while bootstrapping `scry_test_engine_core` as this package's first real downstream consumer. `ScryCore.Grammar`/`ScryCore.GrammarCompose` call Ichor's raw pipeline (`Aether.Parser`, `Grammar.Analysis`, `Grammar.VM`) directly, so `ichor` is a genuine compile-time dependency of scry_core's own `lib/`, not just of its test suite. Mix does not propagate an `only:`-scoped dependency transitively under any circumstance -- verified by also declaring `ichor` directly in the downstream package's own `mix.exs`, which did not help; `mix compile` for scry_core-as-a-dependency only ever draws on scry_core's *own* declared dependency graph. This is a deliberate, temporary trade against Ichor's own recommended production pattern (`ichor` should never ship to a real release), tracked as a confirmed-blocking item in impl_spec.md's Open Implementation Risks until the real `mix ichor.gen`-equivalent Mix compiler task (impl_spec.md §4) exists and lets this go back to dev/test-only.
- `priv/grammar.aether`: `where:where_clause?` and `items:literal_list?` renamed to bare `where_clause?`/`literal_list?` -- explicitly naming an optional (`?`) *rule* reference was found to produce a second, spurious raw-text capture alongside the properly-dispatched one under the rule's own implicit self-capture name (the same pathology `select_ep1a?` was already written to avoid, now confirmed general rather than specific to that one case). Does not affect optional *token* references (`neg:KW_NOT?` is unaffected).
- `mix.exs`: `sobelow` now runs with `--skip` in `precommit` -- without it, Sobelow ignores `@sobelow_skip` annotations entirely and reports the finding anyway (confirmed empirically, not documented anywhere in Sobelow's own output). `ScryCore.Grammar.compile/0`'s own low-confidence `Traversal.FileModule` finding (a `File.read` whose path comes from `:code.priv_dir/1` plus a hardcoded literal, not any caller-controlled input) is skipped this way, per AGENTS.md's "a targeted, justified skip, never a blanket suppression" rule -- `Module.register_attribute(__MODULE__, :sobelow_skip, persist: true)` first, so Elixir's own compiler doesn't in turn flag the annotation itself as an unused attribute under `--warnings-as-errors`. Two real, separately-discovered tooling frictions, both now resolved instead of routed around.
- `priv/grammar.aether`'s `STRING` token had no escape handling at all -- `\"` had no special meaning (confirmed by actually running a query containing one: it silently closed the string early, exactly the bug fixing this exposed), so nothing in lang_spec.md §4's own escape list (`\" \' \\ \n \t \uXXXX`) ever worked. Fixed with a new `ESCAPE` token tried before `STRING`'s "any character" fallback at every position, and `ScryCore.Actions.handle_token/3` now resolves the six real escapes over the delimiter-stripped text instead of just slicing it. An unrecognized `\<char>` is deliberately still not rejected -- ordered PEG choice just falls through to the literal-backslash-then-ordinary-character reading, a documented leniency, not an oversight.
- `ScryCore.Executor`: comparisons involving a `%DateTime{}` or `%NaiveDateTime{}` (the new date/timestamp literals, above) now dispatch through `DateTime.compare/2`/`NaiveDateTime.compare/2` instead of Kernel's `== < > <= >=` -- both structs store microseconds as a `{value, precision}` tuple, so two values representing the exact same instant parsed at different precision (`14:00:00.5` vs `14:00:00.500000`) were neither `==` nor correctly ordered by Kernel comparison, confirmed empirically before treating it as a real bug rather than a hypothetical one (`DateTime.compare/2` correctly said `:eq` for a pair Kernel's own `<` said was ordered). `%Date{}` needed no equivalent fix -- no microsecond field, so Kernel's comparison is already exact for it, verified the same way. The same class of struct-ordering problem `%ScryCore.Rational{}` already needed working around for, caught this time by checking for it proactively while adding a new struct-valued literal, rather than after the fact.
